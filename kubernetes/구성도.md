# 클러스터 구성도 — server, agent, 규모별 구성

## 용어 정리 (세 층이 겹쳐 있음)

| 층위 | 이름 | 실체 |
| --- | --- | --- |
| 물리·가상 머신 | 서버, 머신, VM | 실제 하드웨어. "실서버 3대"의 3대 |
| 머신 위에서 도는 k3s/RKE2 프로세스의 **역할** | **server** / **agent** | `k3s server` 또는 `k3s agent` |
| Kubernetes가 보는 단위 | **노드(node)** | `kubectl get nodes`에 나오는 것. 프로세스 하나 = 노드 하나 |

- k3s의 server/agent는 k3s만의 이름. 표준 Kubernetes 용어로는 server = control-plane 노드, agent = worker 노드
- 실서버: 머신 1대 = 프로세스 1개 = 노드 1개. 세 층이 같은 것을 가리킴
- k3d: 컨테이너 1개 = 프로세스 1개 = 노드 1개. 컨테이너 이름(`k3d-lab-server-0`, `k3d-lab-agent-0`)이 역할을 나타냄
- "server 3"은 반드시 **서로 다른 머신 3대**에 server 프로세스를 하나씩. 한 머신에 두 개 띄우면 그 머신이 죽을 때 같이 죽어 의미 없음

## server 프로세스와 agent 프로세스

**server = 컨트롤 플레인 + agent.** server 안에 agent가 하는 일이 전부 들어 있음.

```text
k3s server 프로세스
 ├─ 컨트롤 플레인
 │   ├ API 서버          (kubectl·모든 컴포넌트의 창구)
 │   ├ 스케줄러          (Pod를 어느 노드에 둘지 결정)
 │   ├ 컨트롤러 매니저   (원하는 상태 유지: replica 수 맞추기 등)
 │   └ 데이터 저장소     (SQLite 기본, HA는 내장 etcd)
 └─ agent 부분  ← k3s agent 프로세스와 동일
     ├ kubelet            (Pod 실행·감시, 노드 등록)
     ├ kube-proxy         (Service 트래픽 전달)
     ├ containerd         (컨테이너 런타임)
     └ Flannel CNI        (Pod 네트워크)
```

| 프로세스 | 컨트롤 플레인 | agent 부분 | `kubectl get nodes` |
| --- | --- | --- | --- |
| `server` | O | O | 나타남, ROLES `control-plane` |
| `server --disable-agent` | O | X | 안 나타남 (kubelet이 없어 노드 등록 안 됨) |
| `agent` | X | O | 나타남, ROLES 없음 |

- server만 있어도 Pod가 뜬다. 그래서 agent 0인 클러스터가 가능
- server 0은 불가. 컨트롤 플레인이 없으면 클러스터가 아님
- k3s는 기본적으로 server에 taint를 걸지 않음. 따라서 server에도 Pod가 스케줄됨
- server에 Pod를 막으려면 taint: `--node-taint=CriticalAddonsOnly=true:NoExecute` → 이때는 agent 없이는 Pod가 뜰 곳이 없음

## agent 부분은 어디에 있나

```text
server 1 + agent 2                        server 3 겸임
──────────────────                        ──────────────
컨트롤 플레인  : 1개 (server 안)               컨트롤 플레인  : 3개
agent 부분   : 3개 (server 안 1 + agent 2)   agent 부분 : 3개 (전부 server 안)
```

## agent가 필요한 이유 (server가 다 갖고 있는데도)

핵심: **컨트롤 플레인은 많을수록 좋은 것이 아니라 홀수 몇 개(3 또는 5)만 있어야 한다.**

1. **etcd는 멤버가 많을수록 느려진다.** 쓰기마다 과반 확인을 기다림. 3개면 2개, 7개면 4개 응답 대기. etcd 권고는 3·5, 최대 7. 노드 100대를 전부 server로 두면 오히려 느리고 불안정
2. **컨트롤 플레인 보호.** server에서 앱이 돌면 앱이 자원을 다 쓸 때 API 서버·etcd가 같이 느려짐 → 스케줄링·자동 복구·kubectl 정지. agent로 워크로드를 분리하고 server에 taint를 걸면 앱이 폭주해도 클러스터 제어는 유지
3. **보안 경계.** server에는 etcd 데이터(모든 Secret)와 클러스터 CA 키가 있음. agent에는 없음. 앱 컨테이너가 뚫려 노드까지 장악당해도 agent면 etcd에 접근 불가
4. **사양과 비용.** server는 etcd 때문에 SSD·여유 메모리 필요. agent는 실행할 앱만큼만. GPU 노드 등 특수 용도 머신에 컨트롤 플레인 사양을 맞출 이유 없음

→ 머신이 3대를 넘으면 컨트롤 플레인은 3개로 고정하고 나머지는 agent. 3대 이하에서 agent가 안 보이는 것은 규모가 그 경계 아래라서.

## etcd 쿼럼 (server 수를 정하는 근거)

| server 수 | 과반 | 허용 장애 | 평가 |
| --- | --- | --- | --- |
| 1 | 1 | 0대 | 학습·개발 |
| 2 | 2 | 0대 | 1대보다 나쁨. 한 대만 죽어도 과반 미달 |
| 3 | 2 | 1대 | 실무 표준 |
| 5 | 3 | 2대 | 대규모 |

짝수는 의미 없음(허용 장애 수가 홀수-1과 같음).

## 규모별 추천 구성

### 1대 — 학습·개발

```text
머신 1
 └ server
   ├ 컨트롤 플레인 (SQLite)
   └ kubelet → Pod 실행
```

- k3d 퀵스타트(`k3d cluster create mycluster`)가 이 형태
- 머신이 죽으면 전부 정지. HA 없음

### 2~3대 — 개발·스테이징 (server 1 + agent N)

```text
머신 1 (server)           머신 2 (agent)           머신 3 (agent)
 ├ 컨트롤 플레인           └ kubelet → Pod          └ kubelet → Pod
 └ kubelet → Pod
```

- 설치: 머신 1에 `k3s server`, 머신 2·3에 `K3S_URL=https://머신1:6443 K3S_TOKEN=... k3s agent`
- API 접점은 머신 1 주소 그대로. VIP 불필요
- 머신 1이 죽으면 앱은 계속 돌지만 배포·자동 복구·kubectl 불가 → **운영에는 부적합**
- 역할 구분과 Pod 분산을 눈으로 보기 좋아 학습용으로 적합. 로컬 `lab`(server 1 + agent 2)이 이것

### 3대 — 소규모 운영 (server 3 겸임)

```text
        API 고정 접점 (kube-vip VIP 또는 L4 LB)
                 │
   ┌─────────────┼─────────────┐
머신 1         머신 2         머신 3
 server         server         server
 ├ etcd 1       ├ etcd 2       ├ etcd 3
 ├ API 등       ├ API 등       ├ API 등
 └ kubelet→Pod  └ kubelet→Pod  └ kubelet→Pod
```

- 3대에서 HA(1대 장애 허용)가 되는 **유일한** 구성
- taint 없음. 워크로드도 3대에서 실행 → 컨트롤 플레인 보호는 양보
- 안전장치: 모든 워크로드에 `resources.requests/limits`, 노드 메모리 70% 이내
- API 접점이 필요해짐: server가 3대라 kubeconfig·조인 주소를 하나로 고정해야 함 (kube-vip VIP 또는 사내 L4 LB)
- 2대 동시 장애 → 과반 미달 → API 정지. 정상 동작이며 3대 구성의 한계
- 실서버 온프레미스 3대의 표준

### 5대 이상 — 표준 운영 (server 3 + agent N)

```text
        API 고정 접점
                 │
   ┌─────────────┼─────────────┐
머신 1         머신 2         머신 3          ← server 3 (taint: Pod 안 받음)
 server         server         server
 └ etcd         └ etcd         └ etcd
   ─────────────┴─────────────┴─────────────
머신 4         머신 5         머신 6 ...      ← agent N (워크로드 전용)
 agent          agent          agent
```

- 컨트롤 플레인 3개 고정, agent는 워크로드만큼 추가
- server에 taint를 걸어 컨트롤 플레인 보호
- agent 추가 = 토큰 넘겨 조인. 클러스터 확장에서 가장 쉬운 작업
- 온프레미스 프로덕션의 기본형

## 로컬(k3d)과 실서버의 3이 다른 이유

| | 로컬 `lab` | 실서버 3대 |
| --- | --- | --- |
| 제약 | 메모리, 학습 시간 | 머신 수 |
| 목표 | 역할 구분·Pod 분산 이해 | 1대 장애 허용 |
| 구성 | server 1 + agent 2 | server 3 겸임 |
| 포기한 것 | HA (PC 한 대라 무의미) | 컨트롤 플레인 보호 |

- 로컬에서 server 3개는 HA가 아님. 컨테이너 3개가 같은 PC 위에 있어 PC가 꺼지면 다 꺼짐
- 실서버 3대 겸임을 k3d로 흉내: `servers: 3, agents: 0`. etcd 3멤버·과반 동작·노드 정지 리허설은 재현됨. LB 컨테이너(serverlb)가 단일이라 그 부분만 HA 흉내 불가

```yaml
# k3d-lab3.yaml — 실서버 3대 겸임 흉내
apiVersion: k3d.io/v1alpha5
kind: Simple
metadata:
  name: lab3
servers: 3
agents: 0
image: rancher/k3s:v1.35.5-k3s1
kubeAPI:
  hostIP: "127.0.0.1"
  hostPort: "61119"
ports:
  - port: 8082:80
    nodeFilters: [loadbalancer]
  - port: 8444:443
    nodeFilters: [loadbalancer]
```

```bash
k3d cluster create --config k3d-lab3.yaml
kubectl get nodes                      # 3대 ROLES control-plane,etcd,master
k3d node stop k3d-lab3-server-1        # 1대 정지 → kubectl 계속 응답
k3d node stop k3d-lab3-server-2        # 2대 정지 → 과반 미달 → API 정지 (정상)
k3d node start k3d-lab3-server-2       # 1대 복구 → 과반 회복 → 재개
```

## k3d ↔ 실서버 대응

| 실서버 3대 | k3d | 비고 |
| --- | --- | --- |
| 머신 (server 3대) | `k3d-lab3-server-0/1/2` 컨테이너 | 컨테이너 1개 = 머신 1대 |
| 내장 etcd 3멤버 | 자동 | server 2개 이상이면 k3d가 첫 노드에 `--cluster-init` |
| API 고정 접점 (kube-vip / LB) | `k3d-lab3-serverlb` | nginx 컨테이너가 6443을 3대로 분산 |
| 진입 VIP (MetalLB) + Traefik | serverlb 80/443 → 각 노드 Traefik | 호스트 포트 매핑으로 대신 |
