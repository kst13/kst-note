# 운영 — 로그, 자원, 문제 해결

[4. 앱 배포](4.%20앱%20배포%20(Jenkins%20Nexus%20Rancher).md)로 올린 앱을 운영하며 자주 묻는 것을 모은다. 로그를 어디서 어떻게 보는지, 노드 자원이 왜 한쪽에 몰리는지, 자주 만나는 오류를 어떻게 푸는지 다룬다.

## 1. 로그는 어디에 쌓이나

컨테이너가 stdout·stderr로 쓴 로그는 **그 Pod가 떠 있는 노드의 파일**로 남는다.

```text
/var/log/pods/<네임스페이스>_<Pod 이름>_<Pod UID>/<컨테이너 이름>/0.log
```

- **실제 위치:** 설치할 때 `/var/log/pods`를 `/app/rke2/log-pods`에 bind mount 했다. 그래서 노드에서는 `/app/rke2/log-pods/...`로 보인다. 같은 파일이다.
- **`0.log`:** 숫자는 컨테이너 재시작 횟수다. 재시작하면 `1.log`가 생긴다. 이름은 kubelet이 정하므로 바꿀 수 없다.
- **크기 제한:** kubelet이 파일당 10Mi, 5개까지 남기고 오래된 것을 지운다. 오래 보관하는 곳이 아니다.
- **Pod가 지워지면** 그 폴더도 지워진다. 배포로 Pod가 바뀌면 이전 로그는 사라진다.
- **앱이 파일로 쓰는 로그**(`/app/logs`)는 emptyDir이라 이 경로에 없다. Pod 안에서만 보이고 Pod와 함께 사라진다.

## 2. 지금 로그 보는 방법

### Rancher 화면

Pod ⋮ → **View Logs**. 최근 일부만 보여 준다. 오래된 로그나 여러 Pod를 같이 보기에는 맞지 않는다.

### kubectl

```bash
kubectl -n <ns> logs deploy/<앱> --tail=200 -f        # 따라가며 보기
kubectl -n <ns> logs <pod> --since=1h                  # 최근 1시간
kubectl -n <ns> logs <pod> --previous                  # 재시작 전 컨테이너 (죽은 이유)
kubectl -n <ns> logs -l app=<앱> --tail=100 --prefix   # 여러 Pod 를 한 번에
```

`--previous`가 `not found`면 그 Pod는 재시작한 적이 없다. 다른 Pod로 교체된 경우에는 이전 Pod 로그가 이미 없다.

### 개발자 PC에서 보기

Rancher에서 kubeconfig를 받으면 PC에서 바로 볼 수 있다. 노드에 접속할 필요가 없다.

1. Rancher → 클러스터 `dev` → 오른쪽 위 **Download KubeConfig**.
2. PC의 `~/.kube/config`로 저장한다. 여러 클러스터면 `KUBECONFIG` 환경변수로 나눠 쓴다.
3. 권한은 Rancher 사용자 권한을 그대로 따른다. 개발자에게는 해당 프로젝트·네임스페이스 읽기 권한만 준다.

```bash
kubectl get ns                                           # 접속 확인
stern -n <ns> <앱>                                       # 여러 Pod 로그를 색으로 구분해 따라감
stern -n <ns> <앱> --since 30m | grep -i exception
k9s -n <ns>                                              # 터미널 화면에서 Pod 선택 → l 로 로그
```

- **stern:** 이름이 맞는 Pod 전부의 로그를 한 화면에 이어 준다. 교체되는 새 Pod도 자동으로 따라간다.
- **k9s:** 터미널용 쿠버네티스 화면이다. Pod 목록, 로그, 셸, 재시작을 키보드로 한다.
- kubeconfig에는 토큰이 들어 있다. git이나 메신저에 올리지 않는다.

## 3. 로그를 모아 두려면: Rancher Logging

### 무엇을 하나

**Rancher Logging은 로그를 다른 곳으로 보내기만 한다.** 저장하거나 검색하는 화면은 없다. Apps → Charts의 Logging 차트로 설치한다.

```text
각 노드의 /var/log/pods ──▶ Fluent Bit (DaemonSet, 노드마다)  파일을 읽어 넘김
                          ──▶ Fluentd (모아서 가공·전송)
                          ──▶ ClusterOutput 이 가리키는 곳 (Loki, Elasticsearch, S3 ...)
```

| 리소스 | 하는 일 |
|---|---|
| ClusterFlow / Flow | 어떤 로그를 보낼지 고른다 (네임스페이스, 라벨). Flow는 한 네임스페이스 안 |
| ClusterOutput / Output | 어디로 보낼지 정한다 (주소, 인증) |

### 설치할 때 고른 것

| 항목 | 값 | 이유 |
|---|---|---|
| Install into Project | **System** | 클러스터 전체 로그를 다루는 시스템 구성요소다. 앱 프로젝트와 권한을 나눈다 |
| Customize Helm options | 끔 | 기본값으로 충분하다 |
| Override the Default Container Registry | 끔 | 이미지 받기가 막힐 때만 Nexus 주소를 넣는다 |
| Docker Root Directory | 비움 | Docker를 쓰지 않는다 (containerd) |
| systemd Log Path | `/run/log/journal` 그대로 | Rocky 기본 journald 위치. 노드 시스템 로그를 읽을 때 쓴다 |

### 받을 곳이 있어야 쓸모가 있다

ClusterOutput이 가리킬 저장소가 없으면 설치만 된 상태다. 예정 구성은 다음과 같다.

```yaml
apiVersion: logging.banzaicloud.io/v1beta1
kind: ClusterOutput
metadata:
  name: loki
  namespace: cattle-logging-system
spec:
  loki:
    url: http://<LOKI_HOST>:3100
    configure_kubernetes_labels: true
---
apiVersion: logging.banzaicloud.io/v1beta1
kind: ClusterFlow
metadata:
  name: apps
  namespace: cattle-logging-system
spec:
  match:
    - exclude:
        namespaces: [kube-system, cattle-system, cattle-logging-system]
    - select: {}
  globalOutputRefs: [loki]
```

### 왜 Loki를 클러스터 밖에 두나

| 선택지 | 판단 |
|---|---|
| Loki + Grafana를 DEV 클러스터 안에 | DEV 노드 RAM이 7.4Gi이고 앱을 절반만 올린 상태다. 앱이 다 올라오면 자리가 모자란다 |
| **Loki + Grafana를 별도 VM(docker compose)에** | 클러스터 자원을 쓰지 않는다. 클러스터가 죽어도 로그를 본다. stage·prod도 같은 곳으로 보낼 수 있다 |
| Sumo Logic 등 SaaS | 로그가 외부로 나간다. 사내 정책 확인이 먼저다 |

- **Loki:** 로그를 라벨(네임스페이스, 앱, Pod)로 묶어 저장하는 서버다. 본문 전체를 색인하지 않아 가볍다.
- **Grafana:** Loki에 쿼리를 보내 로그를 검색·조회하는 화면이다.
- **Fluent Bit:** 노드의 로그 파일을 읽어 다른 곳으로 보내는 가벼운 수집기다. Rancher Logging이 노드마다 띄운다.

그 전까지는 2장의 kubectl, stern, k9s로 본다.

## 4. 노드 자원

### 확인 명령

```bash
kubectl top nodes
kubectl top pods -A --sort-by=memory | head -20
kubectl describe node <노드> | sed -n '/Allocated resources/,/Events/p'   # requests·limits 합계
kubectl get pods -A -o wide --field-selector spec.nodeName=<노드>
```

- **`top`은 실제 사용량이다.** 스케줄러는 실제 사용량이 아니라 `requests` 합계로 자리를 판단한다. 둘을 따로 본다.
- **`requests`:** 이만큼은 보장해 달라는 값이다. 노드 합계가 꽉 차면 새 Pod가 Pending이 된다.
- **`limits`:** 이 이상은 못 쓴다는 값이다. 메모리를 넘기면 OOMKilled, CPU를 넘기면 느려진다.

### 한 노드만 사용률이 높을 때

앱 Pod가 다른 노드에 있어도 dev-1처럼 처음 만든 노드가 높게 나올 수 있다.

| 원인 | 확인 |
|---|---|
| MetalLB L2: VIP를 가진 노드로 모든 요청이 먼저 들어옴 | `kubectl -n metallb-system logs ds/speaker --all-containers \| grep -i announc` |
| etcd 리더, controller-manager·scheduler 리더 | `kubectl -n kube-system get lease` |
| Rancher agent, metrics-server, CoreDNS, Logging 같은 시스템 Pod | 위 `--field-selector spec.nodeName=` 명령 |
| 재시작을 반복하는 Pod | `kubectl get pods -A \| awk '$5>5'` |

노드 안에서는 `top`이나 `ps aux --sort=-%mem | head`로 etcd, kube-apiserver, containerd 중 무엇이 쓰는지 본다.

### requests·limits 조정

처음 값은 짐작이다. 앱이 며칠 돈 뒤 `kubectl top pods`의 평소 사용량을 보고 차트 `resources`를 고친다.

| 종류 | 처음 값 | 조정 기준 |
|---|---|---|
| 웹(nginx) | requests 50m / 64Mi, limits 500m / 256Mi | 대부분 넉넉하다 |
| WAS(Spring) | requests 250m / 768Mi, limits 1 CPU / 1Gi | 평소 메모리 + 30%를 requests로. limits는 힙(75%)을 생각해 잡는다 |

## 5. 자주 만난 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| WAS가 CrashLoopBackOff | DB·Redis 방화벽이 DEV 노드 출발로 안 열림 | 방화벽 요청. 열릴 때까지 `overrides.replicas: 0` |
| 재시작이 계속 반복되는데 횟수 제한을 걸고 싶음 | Deployment는 재시도 횟수 설정이 없다. 대기 시간이 최대 5분까지 늘 뿐이다 | replicas 0으로 멈춤 |
| Upgrade가 `conflict with "agent" ... .spec.replicas` | Rancher 화면에서 Scale함 | Deployment 삭제 후 Upgrade. [4. 앱 배포](4.%20앱%20배포%20(Jenkins%20Nexus%20Rancher).md) 8.4 |
| Installed Apps가 failed | Upgrade 중 실패 | 원인을 고친 뒤 같은 화면에서 다시 Edit/Upgrade. uninstall하지 않는다 |
| 웹 화면은 뜨는데 특정 API만 502 | 그 백엔드가 아직 없거나 방화벽 | `kubectl -n <ns> logs deploy/<웹>`에서 upstream 오류 확인 |
| 웹 Pod가 시작하자마자 죽음 | values의 필수 주소가 비어 템플릿에 `${...}`가 남음 | 차트 렌더링 결과의 env 확인 |
| 이미지 `ImagePullBackOff` | 경로의 환경 부분(`dev/`)이나 태그가 틀림 | `kubectl -n <ns> describe pod <pod>`의 Events |
| `--previous` 로그가 `not found` | 재시작한 적이 없거나 Pod가 교체됨 | 새 Pod 로그를 보거나 stern으로 미리 따라감 |

## 6. 인증서

- **위치:** Traefik 기본 인증서와 추가 인증서는 `kube-system`의 TLS Secret이다. 만드는 법과 추가하는 법은 [3. DEV 클러스터 설치](3.%20DEV%20클러스터%20설치.md) 10.4.
- **만료 확인:**

```bash
kubectl -n kube-system get secret <이름> -o jsonpath='{.data.tls\.crt}' | base64 -d \
  | openssl x509 -noout -subject -enddate
```

- **갱신:** 같은 이름의 Secret을 새 파일로 덮어쓴다. Traefik이 바로 다시 읽는다. 앱은 건드리지 않는다.
