# 부록: Mac(Apple Silicon)에서 Lima로 Rancher 실습 환경 만들기

[[1.  설치 선행|설치 선행]]과 [[2. 설치|설치]] 문서를 실서버에 적용하기 전에, Mac에 VM 7대를 띄워 같은 순서로 연습하기 위한 문서다. 이 문서는 VM과 네트워크를 준비하고, 두 문서를 따라갈 때 실습 환경에서 달라지는 부분만 안내한다.

## 0. 먼저 읽기

### 0.1 전체 진행 순서

위에서부터 차례로 진행한다. 이 문서와 설치 문서를 오가므로 "문서" 열을 확인한다.

| 순서 | 할 일 | 문서 | 실행 위치 |
|---|---|---|---|
| 1 | Homebrew, Lima 설치 | 이 문서 2.1 | Mac |
| 2 | 실습망 준비 (socket_vmnet, networks.yaml, sudoers) | 이 문서 2.2~2.4 | Mac |
| 3 | VM 템플릿, 디스크, VM 만들기 | 이 문서 3장 | Mac |
| 4 | 고정 IP, `/app` 디스크 | 이 문서 4장 | lb, mgmt-1~3 |
| 5 | HAProxy, DNS | 이 문서 5장 | lb, Mac |
| 6 | 선행조건 1.1~1.7 | 선행 문서 + 이 문서 6장 | mgmt-1~3 |
| 7 | 설치 0~3단계 | 설치 문서 | mgmt-1 |
| 8 | Canal 인터페이스 고정 | 이 문서 7.2 | mgmt-1 |
| 9 | 설치 4~5단계 | 설치 문서 + 이 문서 7.3 | mgmt-1 |
| 10 | 조인 토큰 전달 | 이 문서 7.4 | Mac |
| 11 | 설치 6단계 (MGMT-2, MGMT-3 조인) | 설치 문서 | mgmt-2, mgmt-3 |
| 12 | 실습용 CA와 Rancher 인증서 만들기 | 이 문서 7.5 | mgmt-1, Mac |
| 13 | 설치 7~10단계 (Helm, 인증서, Rancher) | 설치 문서 + 이 문서 7.3 | mgmt-1, Mac |
| 14 | DEV 클러스터 | 이 문서 8장 | Mac, dev-1~3, 브라우저 |

설치 문서의 입력값은 7.1 표를 보고 넣는다.

### 0.2 읽는 법

- 코드 블록 첫 줄의 `# [Mac]`, `# [mgmt-1]`, `# [모든 VM]`이 실행 위치다. VM에서 실행하라는 블록은 Mac 터미널에서 `limactl shell <VM이름>`으로 VM에 들어간 뒤 붙여넣는다.
- 블록은 한 번에 하나씩 붙여넣는다. 블록마다 끝에 있는 "정상" 기준을 확인하고 다음으로 넘어간다.
- VM 블록에서 입력값 검사가 실패하면 이유를 출력하고 `exit 1`로 VM 셸을 닫는다. Mac 프롬프트로 돌아오면 원인을 고친 뒤 다시 `limactl shell`로 들어가 그 블록을 처음부터 실행한다.
- 실습 파일은 Mac의 `~/lima-lab`에 둔다. 인증서, 토큰, kubeconfig가 Obsidian 동기화 폴더에 들어가지 않도록 vault 밖에 둔다.

### 0.3 용어

| 용어 | 뜻 |
|---|---|
| Lima | Mac에서 Linux VM을 명령어로 만들고 관리하는 도구. 명령은 `limactl` |
| socket_vmnet | VM끼리, 그리고 Mac과 VM이 서로 통신하는 가상 네트워크를 만드는 프로그램 |
| vz | macOS 내장 가상화(Apple Virtualization). QEMU보다 빠르다 |
| sparse 디스크 | 크기를 40GiB로 만들어도 실제로 쓴 만큼만 Mac 디스크를 차지하는 디스크 |
| cloud-init | VM이 처음 켜질 때 계정, 네트워크 등을 자동으로 설정하는 프로그램 |
| HAProxy | 들어온 연결을 여러 서버로 나눠 보내는 프로그램. 여기서는 L4 장비 대신 쓴다 |
| TCP 패스스루 | 암호화된 연결을 풀지 않고 그대로 뒤쪽 서버로 넘기는 방식 |
| SAN | 인증서에 적힌 "이 인증서를 쓸 수 있는 도메인 목록" |

## 1. 구성

기준 PC: M1 Max, 메모리 64GB, 여유 디스크 약 130GB, macOS 26.

| VM | 실습 IP | 실서버 IP | vCPU, 메모리 | 루트 디스크, `/app` 디스크 | 역할 |
|---|---|---|---|---|---|
| `lb` | 192.168.105.108 | 10.10.10.108 (L4 VIP) | 1, 1GiB | 10GiB, 없음 | HAProxy |
| `mgmt-1` | 192.168.105.109 | 10.10.10.109 | 4, 8GiB | 30GiB, 40GiB | 첫 RKE2 server |
| `mgmt-2` | 192.168.105.110 | 10.10.10.110 | 4, 8GiB | 30GiB, 40GiB | RKE2 server |
| `mgmt-3` | 192.168.105.111 | 10.10.10.111 | 4, 8GiB | 30GiB, 40GiB | RKE2 server |
| `dev-1` | 192.168.105.56 | 10.10.12.56 | 2, 6GiB | 30GiB, 40GiB | DEV Custom 클러스터 |
| `dev-2` | 192.168.105.57 | 10.10.12.57 | 2, 6GiB | 30GiB, 40GiB | 위와 같음 |
| `dev-3` | 192.168.105.58 | 10.10.12.58 | 2, 6GiB | 30GiB, 40GiB | 위와 같음 |

- 7대를 모두 켜면 메모리 43GiB를 쓴다. macOS와 브라우저 몫으로 약 20GB가 남는다. Rancher Desktop은 자체 VM으로 메모리를 따로 쓰므로 실습 중에는 종료한다.
- 디스크는 sparse라 처음엔 작지만, 이미지와 etcd가 쌓이면 VM당 8~15GB씩 늘어난다. 7대 기준 실제 사용량은 약 70~90GB다.
- DEV 3대는 MGMT와 Rancher 설치가 끝난 뒤(순서 14) 켠다. 그 전까지는 메모리 25GiB 정도만 쓴다.

### 실서버와 다른 점

| 항목 | 실서버 | Lima 실습 |
|---|---|---|
| CPU 아키텍처 | x86_64 (amd64) | aarch64 (arm64). 내려받는 파일 이름이 다르다 (7.3) |
| 네트워크 | MGMT 10.10.10.x와 DEV 10.10.12.x가 분리되고 사이에 사내 방화벽 | 모두 192.168.105.0/24 한 대역. 대역 사이 방화벽은 연습할 수 없다 |
| 네트워크 카드 | 1개 | 2개. `eth0`은 Lima 관리용으로 모든 VM이 같은 IP(192.168.5.15), `lima0`이 실습망 |
| L4 장비 | 인프라팀 장비 | `lb` VM의 HAProxy |
| DNS | 사내 DNS | Lima 내장 DNS 설정과 Mac의 `/etc/hosts` |
| 사내 CA | 보안팀 발급 | 직접 만든 실습용 CA (7.5) |
| Nexus | 사내 Nexus | 다루지 않는다 |

> [!warning] Rancher arm64 지원 여부를 먼저 확인한다
> RKE2는 arm64를 지원한다. Rancher 2.15.2 Management의 arm64 지원 여부는 시작 전에 [Rancher 2.15.2 Support Matrix](https://www.suse.com/suse-rancher/support-matrix/all-supported-versions/rancher-v2-15-2/)에서 확인한다. 지원 범위 밖이면 이 실습은 설치 순서를 익히는 용도로만 쓰고, 결과를 운영 환경의 근거로 쓰지 않는다.

## 2. Mac 준비

### 2.1 Homebrew와 Lima 설치

```bash
# [Mac] Homebrew 설치 확인. "command not found"가 나오면 https://brew.sh 의 안내대로 먼저 설치
brew --version
# Lima 설치. 이미 있으면 최신으로 올림
brew install lima || brew upgrade lima
# 버전 확인. 이 문서의 템플릿은 2.0 이상이 필요
limactl --version
```

정상: `limactl version 2.x.x`가 출력된다.

### 2.2 socket_vmnet 설치

Lima 기본 네트워크로는 VM끼리 통신할 수 없다. VM끼리, 그리고 Mac과 VM이 통신하려면 `socket_vmnet`이 필요하다.

`socket_vmnet`은 root 권한으로 실행된다. 일반 사용자가 이 파일을 바꿔치기하면 그 파일이 root로 실행되므로, Lima는 root만 수정할 수 있는 경로에 있는 파일만 실행한다. Homebrew 경로(`/opt/homebrew`)는 일반 사용자가 쓸 수 있으므로 `/opt/socket_vmnet`으로 복사한다.

```bash
# [Mac] socket_vmnet 설치
brew install socket_vmnet
# root만 수정할 수 있는 경로를 만들고 복사
sudo mkdir -p /opt/socket_vmnet/bin
sudo install -o root -g wheel -m 755 "$(brew --prefix)/opt/socket_vmnet/bin/socket_vmnet" /opt/socket_vmnet/bin/socket_vmnet
# 확인
ls -l /opt/socket_vmnet/bin/socket_vmnet
```

정상: 소유자가 `root`로 표시된다.

### 2.3 실습망 설정 (networks.yaml)

실습망 `shared`는 DHCP로 192.168.105.2~254를 나눠준다. 1장의 고정 IP(.56~.58, .108~.111)와 겹치지 않도록 DHCP 범위를 .49까지로 줄인다. 같은 파일에 남아 있는 `vdeSwitch`, `vdeVMNet` 두 줄은 Lima 2.x에서 지원하지 않아 `limactl`을 실행할 때마다 경고를 내므로 함께 지운다.

이 파일은 실행 중인 VM이 없을 때 고친다.

```bash
# [Mac] 실행 중인 VM이 없는지 확인. STATUS가 모두 Stopped이거나 목록이 비어 있어야 함
limactl list
# 원본 백업
cp ~/.lima/_config/networks.yaml ~/.lima/_config/networks.yaml.bak
# shared 망의 DHCP 끝 주소를 .49로 바꾸고, 지원하지 않는 vde 두 줄을 삭제
sed -i '' \
  -e 's/^\( *dhcpEnd: \)192\.168\.105\.254/\1192.168.105.49/' \
  -e '/^ *vdeSwitch:/d' \
  -e '/^ *vdeVMNet:/d' \
  ~/.lima/_config/networks.yaml
# 바뀐 부분 확인
diff ~/.lima/_config/networks.yaml.bak ~/.lima/_config/networks.yaml
```

정상: `diff` 결과에 `vdeSwitch`, `vdeVMNet` 삭제와 `dhcpEnd: 192.168.105.49` 변경, 이 세 가지만 보인다. `192.168.106.254`(host 망)는 바뀌지 않아야 한다.

### 2.4 sudoers 설치

sudoers는 어떤 사용자가 어떤 명령을 `sudo`로 실행할 수 있는지 정한 규칙 파일이다. `limactl`은 일반 사용자 권한으로 실행되므로, `socket_vmnet`을 정해진 경로와 인자로 실행하는 것만 비밀번호 없이 허용하는 규칙을 `/etc/sudoers.d/lima`에 넣는다.

이 규칙에는 2.3에서 고친 값(`--vmnet-dhcp-end` 등)이 그대로 들어간다. Lima는 VM을 켤 때마다 설치된 규칙과 지금 만들 규칙을 비교해서, 다르면 VM을 켜지 않는다. 그래서 반드시 2.3을 끝낸 뒤에 설치한다.

```bash
# [Mac] 현재 networks.yaml 기준으로 규칙 생성
limactl sudoers > /tmp/etc_sudoers.d_lima
# 내용 확인. socket_vmnet 경로와 --vmnet-dhcp-end=192.168.105.49 가 보여야 함
cat /tmp/etc_sudoers.d_lima
# 문법 검사. 오류가 있으면 설치하지 않음 (잘못된 sudoers는 sudo 전체를 막을 수 있음)
sudo visudo -cf /tmp/etc_sudoers.d_lima
# root 소유, 읽기 전용으로 설치
sudo install -o root -g wheel -m 440 /tmp/etc_sudoers.d_lima /etc/sudoers.d/lima
rm /tmp/etc_sudoers.d_lima
```

정상: `visudo`가 `parsed OK`를 출력한다.

다음 경우에는 2.4를 다시 한다. 하지 않으면 VM을 켤 때 sudoers 불일치 오류가 난다.

| 변경 | 다시 할 것 |
|---|---|
| `networks.yaml` 수정 | 2.4 |
| Lima 업그레이드 | 2.4 |
| socket_vmnet 업그레이드 | 2.2의 복사, 2.4 |

## 3. VM 만들기

### 3.1 공통 템플릿

모든 VM이 이 템플릿을 같이 쓰고, VM마다 다른 CPU, 메모리, 디스크만 3.3에서 바꾼다.

```bash
# [Mac] 실습 폴더를 만들고 템플릿 파일 생성
mkdir -p ~/lima-lab
cat > ~/lima-lab/rocky9-node.yaml <<'EOF'
minimumLimaVersion: 2.0.0

# Lima에 내장된 Rocky 9 클라우드 이미지 (aarch64). 홈 폴더 공유 설정은 가져오지 않음
base:
- template:_images/rocky-9

vmType: vz
cpus: 4
memory: 8GiB
disk: 30GiB

# Mac 홈 폴더 공유를 끔. 실서버처럼 격리하고, 파일은 limactl copy로 옮김
mounts: []

# Lima는 기본으로 VM 안에 별도 containerd를 설치함.
# RKE2의 containerd와 충돌하고 선행 문서 1.5 점검도 실패하므로 끔
containerd:
  system: false
  user: false

# 실습망 연결. VM 안에서 lima0 인터페이스로 보임
networks:
- lima: shared

# VM과 Pod가 Rancher 도메인을 lb로 찾도록 Lima 내장 DNS에 등록
hostResolver:
  hosts:
    rancher.lab.internal: 192.168.105.108
EOF
# 문법 확인
limactl validate ~/lima-lab/rocky9-node.yaml
```

정상: 마지막 줄에 `rocky9-node.yaml: OK`가 나온다.

### 3.2 `/app` 디스크 만들기

선행 문서 1.6(bind mount)을 연습하기 위한 추가 디스크다. VM과 따로 관리되므로 VM을 지워도 남는다.

```bash
# [Mac] MGMT, DEV 6대용 40GiB 디스크 생성
for n in mgmt-1 mgmt-2 mgmt-3 dev-1 dev-2 dev-3; do
  limactl disk create "${n}-app" --size 40GiB
done
limactl disk ls
```

정상: `mgmt-1-app`부터 `dev-3-app`까지 6개가 보인다.

### 3.3 VM 만들고 켜기

```bash
# [Mac]
cd ~/lima-lab

# MGMT 3대: 템플릿 기본값(4 vCPU, 8GiB)에 /app 디스크 연결. 포맷은 VM 안에서 직접 함
for n in mgmt-1 mgmt-2 mgmt-3; do
  limactl create --name "$n" --tty=false \
    --set ".additionalDisks = [{\"name\": \"${n}-app\", \"format\": false}]" \
    ./rocky9-node.yaml
done

# DEV 3대: 2 vCPU, 6GiB
for n in dev-1 dev-2 dev-3; do
  limactl create --name "$n" --tty=false \
    --set ".cpus = 2 | .memory = \"6GiB\" | .additionalDisks = [{\"name\": \"${n}-app\", \"format\": false}]" \
    ./rocky9-node.yaml
done

# lb 1대: 1 vCPU, 1GiB, 루트 10GiB, 추가 디스크 없음
limactl create --name lb --tty=false \
  --set '.cpus = 1 | .memory = "1GiB" | .disk = "10GiB"' \
  ./rocky9-node.yaml

# lb와 MGMT만 켬. 처음에는 Rocky 이미지(수백 MB)를 내려받느라 몇 분 걸림
for n in lb mgmt-1 mgmt-2 mgmt-3; do limactl start "$n"; done

limactl list
```

정상: `lb`, `mgmt-1~3`은 `Running`, `dev-1~3`은 `Stopped`이고 VMTYPE이 `vz`, ARCH가 `aarch64`다.

### 3.4 VM 접속

```bash
# [Mac] mgmt-1에 접속. 나올 때는 exit
limactl shell mgmt-1
```

- Mac 사용자 이름과 같은 계정으로 들어가고, `sudo`는 비밀번호를 묻지 않는다.
- VM 안의 hostname은 `lima-mgmt-1` 형태다. RKE2 노드 이름은 설치 문서의 config `node-name`으로 따로 정하므로 바꾸지 않아도 된다.

## 4. VM 기본 설정

### 4.1 고정 IP

`lb`, `mgmt-1`, `mgmt-2`, `mgmt-3`에서 하나씩 실행한다. DEV는 8장에서 한다.

`lima0`은 처음에 DHCP로 IP를 받는다. 실서버처럼 고정 IP로 바꾸고, cloud-init이 다음 부팅 때 다시 DHCP로 되돌리지 않게 막는다.

```bash
# [lb, mgmt-1, mgmt-2, mgmt-3 각각]
# 이 VM의 IP 입력: lb=192.168.105.108, mgmt-1=.109, mgmt-2=.110, mgmt-3=.111
read -r -p '이 VM의 실습 IP: ' LAB_IP
[[ "$LAB_IP" =~ ^192\.168\.105\.[0-9]+$ ]] || { echo "192.168.105.x 형식이 아님: '$LAB_IP'"; exit 1; }

# lima0을 관리하는 NetworkManager 연결 이름 조회
CON=$(nmcli -g GENERAL.CONNECTION device show lima0)
[ -n "$CON" ] || { echo 'lima0 인터페이스 없음: 11장 참고'; exit 1; }

# 고정 IP로 변경. 게이트웨이는 Mac. DNS는 eth0 쪽 Lima DNS를 그대로 씀
sudo nmcli con mod "$CON" ipv4.method manual ipv4.addresses "${LAB_IP}/24" \
  ipv4.gateway 192.168.105.1 ipv4.ignore-auto-dns yes
sudo nmcli con up "$CON"

# 다음 부팅부터 cloud-init이 네트워크 설정을 다시 쓰지 않도록 막음
echo 'network: {config: disabled}' | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg >/dev/null

# 확인
ip -br addr
getent hosts rancher.lab.internal
```

정상:

```text
lo      UNKNOWN  127.0.0.1/8 ...
eth0    UP       192.168.5.15/24 ...
lima0   UP       192.168.105.109/24 ...      ← 입력한 IP
192.168.105.108 rancher.lab.internal
```

4대를 모두 설정했으면 서로 통신과 재부팅 후 유지를 확인한다.

```bash
# [mgmt-1] 다른 VM과 통신 확인
for ip in 192.168.105.108 192.168.105.110 192.168.105.111; do ping -c1 -W2 "$ip" >/dev/null && echo "$ip OK" || echo "$ip 실패"; done
```

```bash
# [Mac] mgmt-1을 껐다 켠 뒤 IP가 그대로인지 확인

limactl shell mgmt-1 ip -br addr show lima0
```

정상: 세 주소 모두 `OK`이고, 재부팅 뒤에도 `lima0`이 192.168.105.109다.

### 4.2 `/app` 디스크 포맷과 마운트

`mgmt-1`, `mgmt-2`, `mgmt-3`에서 하나씩 실행한다. `lb`는 하지 않는다.

```bash
# [mgmt-1, mgmt-2, mgmt-3 각각] 디스크 목록 확인
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT
```

목록에서 SIZE가 `40G`이고 FSTYPE과 MOUNTPOINT가 비어 있는 디스크를 찾는다. 보통 `vdb`다. 30G짜리(`vda`, 루트)나 크기가 작은 cidata 디스크(Lima가 초기 설정용으로 붙이는 디스크)를 고르면 안 된다.

```bash
# [mgmt-1, mgmt-2, mgmt-3 각각] 위에서 찾은 이름 입력 (예: vdb)
read -r -p '/app으로 쓸 디스크 이름: ' APP_DEV
[ -b "/dev/${APP_DEV}" ] || { echo "/dev/${APP_DEV} 없음"; exit 1; }
# 이미 파일시스템이 있으면 중단 (VM을 다시 만들고 기존 디스크를 붙인 경우)
[ -z "$(sudo blkid -o value -s TYPE "/dev/${APP_DEV}")" ] || { echo '이미 포맷된 디스크: lsblk로 다시 확인'; exit 1; }
# xfs로 포맷 (Rocky 기본 파일시스템)
sudo mkfs.xfs "/dev/${APP_DEV}"
# UUID로 fstab에 등록하고 마운트
sudo mkdir -p /app
APP_UUID=$(sudo blkid -s UUID -o value "/dev/${APP_DEV}")
echo "UUID=${APP_UUID} /app xfs defaults 0 0" | sudo tee -a /etc/fstab >/dev/null
sudo systemctl daemon-reload
sudo mount -a
df -h /app
```

정상: `df` 결과에 `/app`이 약 40G로 보인다.

## 5. lb와 DNS

### 5.1 HAProxy (L4 장비 대신)

설치 문서 0.3절의 L4 설정(443, 80, 9345, 6443을 MGMT 3대로 그대로 넘김)을 HAProxy로 만든다.

```bash
# [lb] HAProxy 설치와 원본 설정 백업
sudo dnf install -y haproxy
sudo cp /etc/haproxy/haproxy.cfg /etc/haproxy/haproxy.cfg.orig

# 설정 파일 교체
sudo tee /etc/haproxy/haproxy.cfg >/dev/null <<'EOF'
global
    log /dev/log local0
    maxconn 4096

defaults
    mode tcp
    log global
    option tcplog
    timeout connect 5s
    # Rancher agent의 오래 유지되는 연결(WebSocket)이 끊기지 않도록 1시간
    timeout client 1h
    timeout server 1h

# 443: Rancher 화면과 API. Rancher의 /ping 응답(pong)으로 서버 상태 확인
frontend rancher_https
    bind *:443
    default_backend rancher_https
backend rancher_https
    option httpchk
    http-check send meth GET uri /ping hdr Host rancher.lab.internal
    http-check expect string pong
    default-server check check-ssl verify none check-sni rancher.lab.internal inter 5s fall 3 rise 2
    server mgmt-1 192.168.105.109:443
    server mgmt-2 192.168.105.110:443
    server mgmt-3 192.168.105.111:443

# 80: HTTP
frontend rancher_http
    bind *:80
    default_backend rancher_http
backend rancher_http
    default-server check inter 5s
    server mgmt-1 192.168.105.109:80
    server mgmt-2 192.168.105.110:80
    server mgmt-3 192.168.105.111:80

# 9345: RKE2 server 조인
frontend rke2_register
    bind *:9345
    default_backend rke2_register
backend rke2_register
    default-server check inter 5s
    server mgmt-1 192.168.105.109:9345
    server mgmt-2 192.168.105.110:9345
    server mgmt-3 192.168.105.111:9345

# 6443: Kubernetes API
frontend kube_api
    bind *:6443
    default_backend kube_api
backend kube_api
    default-server check inter 5s
    server mgmt-1 192.168.105.109:6443
    server mgmt-2 192.168.105.110:6443
    server mgmt-3 192.168.105.111:6443
EOF

# SELinux가 HAProxy의 9345, 6443 연결을 막지 않도록 허용
sudo setsebool -P haproxy_connect_any 1
# 문법 검사 후 시작
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl enable --now haproxy
sudo ss -lntp | grep haproxy
```

정상: `Configuration file is valid`가 나오고, `ss` 결과에 80, 443, 6443, 9345 네 포트가 보인다.

아직 RKE2와 Rancher를 설치하지 않았으므로 지금은 모든 뒤쪽 서버가 DOWN으로 나온다. 정상이다. 상태는 `sudo journalctl -u haproxy -f`로 볼 수 있다.

### 7.2 Canal 인터페이스 고정 (설치 3단계 바로 뒤, 4단계 전)

모든 VM의 `eth0`이 같은 IP(192.168.5.15)를 쓴다. Pod 네트워크(Canal의 flannel)가 `eth0`을 고르면 노드끼리 Pod 통신이 안 된다. 그래서 RKE2를 처음 켜기 전에 `lima0`을 쓰도록 고정한다.

```bash
# [mgmt-1] 설치 문서 3단계에서 만든 manifests 폴더에 추가
sudo tee /var/lib/rancher/rke2/server/manifests/rke2-canal-config.yaml >/dev/null <<'YAML'
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: rke2-canal
  namespace: kube-system
spec:
  valuesContent: |-
    flannel:
      iface: "lima0"
YAML
ls /var/lib/rancher/rke2/server/manifests/
```

정상: `rke2-canal-config.yaml`과 `rke2-traefik-config.yaml` 두 파일이 보인다.

RKE2가 뜬 뒤(설치 5단계)에 `kubectl get nodes -o wide`의 INTERNAL-IP가 192.168.105.x인지 확인한다. 192.168.5.15로 나오면 config의 `node-ip`가 잘못 들어간 것이다.

### 7.4 조인 토큰 전달 (설치 6단계 전)

설치 문서 6단계는 mgmt-1의 토큰을 mgmt-2, mgmt-3에 미리 넣어 두라고 한다. 실습에서는 Mac에서 아래처럼 옮긴다. 토큰은 화면에 출력되지 않고 VM 사이로만 지나간다.

```bash
# [Mac] mgmt-1의 server token을 mgmt-2, mgmt-3의 /etc/rancher/rke2/server-token으로 복사
for n in mgmt-2 mgmt-3; do
  limactl shell --workdir / "$n" sudo install -d -m 700 /etc/rancher/rke2
  limactl shell --workdir / mgmt-1 sudo cat /var/lib/rancher/rke2/server/token \
    | limactl shell --workdir / "$n" sudo sh -c 'umask 077; cat > /etc/rancher/rke2/server-token'
  limactl shell --workdir / "$n" sudo stat -c '%a %U %s %n' /etc/rancher/rke2/server-token
done
```

정상: 두 VM 모두 `600 root <0보다 큰 크기> /etc/rancher/rke2/server-token`이 출력된다.

### 7.5 실습용 CA와 Rancher 인증서 (설치 8단계 전)

설치 문서 8.1에 필요한 `tls.crt`, `tls.key`, `cacerts.pem`을 직접 만든다. macOS의 `openssl`은 LibreSSL이라 옵션이 일부 다르므로, mgmt-1 안의 OpenSSL로 만든다.

```bash
# [mgmt-1] 현재 계정만 접근할 수 있는 폴더 생성
install -d -m 700 "$HOME/lab-ca"
cd "$HOME/lab-ca" || exit 1
umask 077
# 1) 실습용 루트 CA (10년)
openssl req -x509 -newkey rsa:4096 -sha256 -days 3650 -nodes \
  -keyout ca.key -out cacerts.pem -subj "/CN=Lab Internal Root CA" \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign"
# 2) Rancher 서버용 개인키와 인증서 요청서
openssl req -newkey rsa:2048 -nodes -keyout tls.key -out tls.csr -subj "/CN=rancher.lab.internal"
# 3) CA로 서버 인증서 발급. SAN에 Rancher 도메인을 넣음
printf 'subjectAltName=DNS:rancher.lab.internal\nextendedKeyUsage=serverAuth\nkeyUsage=critical,digitalSignature,keyEncipherment\n' > san.ext
openssl x509 -req -in tls.csr -CA cacerts.pem -CAkey ca.key -CAcreateserial \
  -out tls.crt -days 825 -sha256 -extfile san.ext
# 확인
openssl x509 -in tls.crt -noout -subject -issuer -ext subjectAltName
# 8.1에 입력할 경로
echo "$HOME/lab-ca"
# 다른 VM과 Mac에 나눠 줄 CA 사본. CA 인증서는 공개해도 되는 파일이라 644
install -m 644 cacerts.pem /tmp/lab-ca.pem
```

정상: `issuer`가 `CN=Lab Internal Root CA`, SAN이 `DNS:rancher.lab.internal`이다.

`ca.key`는 mgmt-1 밖으로 옮기지 않는다. 이 CA를 Mac에서 신뢰하는 동안에는 이 키로 어떤 사이트의 인증서든 만들 수 있기 때문이다.

CA를 mgmt-2, mgmt-3과 Mac으로 옮긴다.

```bash
# [Mac] mgmt-1의 CA 사본을 Mac으로 가져와 mgmt-2, mgmt-3에 복사
limactl copy mgmt-1:/tmp/lab-ca.pem ~/lima-lab/cacerts.pem
for n in mgmt-2 mgmt-3; do limactl copy ~/lima-lab/cacerts.pem "${n}:/tmp/lab-ca.pem"; done
```

```bash
# [mgmt-1, mgmt-2, mgmt-3 각각] OS가 실습 CA를 신뢰하도록 등록
sudo install -m 644 /tmp/lab-ca.pem /etc/pki/ca-trust/source/anchors/lab-ca.pem
sudo update-ca-trust
```

```bash
# [Mac] 로그인 키체인에 실습 CA 신뢰 추가. Mac 로그인 비밀번호를 물을 수 있음
security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db ~/lima-lab/cacerts.pem
```

이제 설치 문서 7~10단계를 진행한다. 10단계까지 끝나면 Mac 브라우저에서 `https://rancher.lab.internal`이 인증서 경고 없이 열려야 한다.

## 8. DEV 클러스터

MGMT와 Rancher 설치가 끝난 뒤에 진행한다.

1. DEV VM 켜기

   ```bash

   ```

   그다음 각 DEV에서 7.5의 `update-ca-trust` 블록을 실행한다.

4. Rancher 화면에서 Custom 클러스터를 만든다. DEV VM도 네트워크 카드가 2개라서 다음 두 가지를 넣는다. 화면 메뉴 이름은 Rancher 버전에 따라 조금 다를 수 있다.

정상: Rancher 화면에서 DEV 클러스터가 `Active`가 되고, 노드 3대의 IP가 192.168.105.56~58로 보인다.

| VM 안에 `lima0`이 없음 | networks.yaml의 `shared` 정의(2.3), 템플릿의 `networks: - lima: shared`(3.1) |
| 재부팅 후 IP가 다시 DHCP로 바뀜 | 4.1의 `99-disable-network-config.cfg`가 있는지, `nmcli con show "$CON"`의 `ipv4.method`가 `manual`인지 |
| 6단계에서 `9345 연결 안 됨` | 설치 4단계에서 mgmt-1의 RKE2가 켜졌는지, lb의 `sudo journalctl -u haproxy`에서 mgmt-1 9345가 UP인지 |
| 노드는 Ready인데 노드끼리 Pod 통신 안 됨 | 7.2의 Canal 설정, `kubectl get nodes -o wide`의 INTERNAL-IP |
| 브라우저 인증서 경고 | Mac 키체인 CA 신뢰(7.5), `/etc/hosts`(5.2), `tls.crt`의 SAN |
| DEV가 계속 Updating | DEV에서 `getent hosts rancher.lab.internal`, CA 신뢰(8장 3번), 8장 4번의 Canal과 IP 설정 |
| Mac이 느려짐 | `limactl list`의 메모리 합계, Rancher Desktop 종료 여부. DEV를 잠시 꺼 둔다 |
