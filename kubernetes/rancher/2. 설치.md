# Rancher 설치 — Rocky Linux 9 · 3노드 RKE2 Management

> [!important] 검증 범위
> 별도 선행조건 문서의 작업을 완료한 MGMT 노드에서 시작하는 Rancher 설치 절차다. OS·방화벽·마운트 준비 명령은 중복 수록하지 않는다. 공식 출처와 미확인 사항을 유지했다. 실제 서버·L4·Nexus에서 실행 검증한 결과는 아니다. 환경값을 확정하고 각 단계의 성공 조건을 확인하면서 진행한다.

대상은 MGMT-1~3 및 Rancher다. 완료 후 [DEV·STAGE 클러스터 설치](02_DEV_STAGE_클러스터_설치.md)를 진행한다.

| cert-manager CRD 삭제 | 일괄 삭제 명령 제거. 기존 Certificate/Issuer와 인증서 운영에 영향을 줄 수 있음 |
| DEV 등록 | Custom 생성과 기존 클러스터 Import는 별개. DEV에 Management 토큰·server 설정 복사 금지 |

> [!important] OS 지원 판정은 아직 조건부
> 열람한 Rancher 2.15.2 표의 RHEL 파생 OS 행에는 9.6/9.8이, RKE2 1.36 표에는 9.7/9.8이 표시되어 있다. 두 표 모두 Rocky를 RHEL 시험의 일부로 취급하는 각주가 있다. RKE2 표는 개정 기준을 1.36.3으로 적으면서 구성 요소 행은 1.36.5를 표시하므로, 이 표만으로 **특정 Rocky minor + 1.36.4 패치 조합을 개별 인증했다고 단정할 수 없다**. 실제 OS minor와 계약 지원 범위를 확인하기 전에는 운영 지원 판정을 보류한다. [Rancher 표](https://www.suse.com/suse-rancher/support-matrix/all-supported-versions/rancher-v2-15-2/), [RKE2 표](https://www.suse.com/suse-rke2/support-matrix/all-supported-versions/rke2-v1-36/)

## 0. 설치 범위와 사용할 구성

|---|---|---|---|

| MGMT-2 | 10.10.10.110 | RKE2 server: etcd + control plane + workload | 운영자 |
| MGMT-3 | 10.10.10.111 | RKE2 server: etcd + control plane + workload | 운영자 |

MGMT 3대는 모두 etcd 투표 멤버다. 1대 장애는 견디지만 2대 장애 시 quorum을 잃는다. DEV 3대도 본문에서는 각각 etcd/control plane/worker 3개 역할을 선택한다. 별도 worker 분리 구성이 필요하면 노드를 추가해야 한다.

### 0.2 실행 규칙

- 명령은 **Rocky Linux의 Bash** 기준이다. 다른 셸에서는 먼저 `bash`를 실행한다. 파이프라인 오류 감지를 위해 세션에서 `set -o pipefail`을 적용한다.
- `sudo`가 있는 명령은 root 권한이다. 나머지는 지정한 관리자 계정에서 실행한다.
- `<사내도메인>` 같은 표기는 설명용 자리표시자다. 이를 셸에 그대로 입력하면 리다이렉션으로 해석될 수 있다. 본문 실행 블록은 `read`로 환경값을 받는다.
- `EOF`/`YAML` 종료 표시는 줄 맨 앞에 둔다. `<<'YAML'`은 변수 치환 없이, `<<YAML`은 변수 치환하여 파일을 만든다.
- 단계별·서버별 블록이다. 문서 전체를 하나의 스크립트로 실행하지 않는다. 오류가 나면 그 단계에서 멈춘다.
- 입력값 검사가 실패하면 이유를 출력한 뒤 `exit 1`로 **현재 셸을 종료**한다. SSH 접속이 끊기면 다시 접속해 그 블록을 처음부터 실행한다. 이전에 입력한 변수는 남아 있지 않다.
- IP는 코드에 고정하지 않고 `read`로 입력받는다. 입력 안내의 예시는 0.1절 실서버 값이다. 노드 자신의 IP는 그 서버에 실제로 있는 주소인지 확인한다.
- 비밀값에 `set -x`를 사용하지 않는다. Obsidian 동기화 폴더에는 토큰, kubeconfig, 키, Helm Secret을 저장하지 않는다.

### 0.3 L4·DNS 요청서

기본은 **L4 TCP 패스스루 + 노드 Traefik TLS 종료**다. L4 TLS offload 방식은 헤더·Rancher TLS 옵션이 달라지므로 이 절차와 혼용하지 않는다.

| VIP listener | backend | 용도/허용 대상 |
|---|---|---|
| TCP 443 | MGMT-1~3:443 | Rancher UI/API, DEV agent의 HTTPS·WebSocket |
| TCP 80 | MGMT-1~3:80 | HTTP 리다이렉트 또는 선택한 인증 방식. 공개 ACME 사용 시 별도 검토 |
| TCP 9345 — 권장 추가 | MGMT-1~3:9345 | MGMT 신규/복구 노드 등록, 클러스터 내부·관리망만 허용 |
| TCP 6443 — 권장 추가 | MGMT-1~3:6443 | Kubernetes API, 클러스터 노드·승인된 관리망만 허용 |

- DNS `rancher.<사내도메인> → 10.10.10.108`. 서버·Pod·관리 PC에서 모두 해석되어야 한다.
- 가능하면 API용 `rke2-api.<사내도메인>`도 같은 VIP에 등록하고 API 인증서 SAN에 포함한다. 본문은 원문 주소 보존을 위해 VIP IP를 조인 주소로 쓴다.
- 443 health check는 실제 SNI/Host를 넣은 HTTPS `/ping` → 200, `pong` 응답 권장. TCP 확인만으로 Rancher 정상 여부는 보장되지 않는다.
- 9345/6443 listener는 각 포트별 health check를 둔다. 장시간 WebSocket 연결과 idle timeout을 검증한다. L4 자체도 이중화되어야 한다.
- L4 9345 추가가 불가하면 6단계의 직접 IP 분기를 쓴다. **443만으로 RKE2 조인은 불가능**하다. [공식 근거 S4](https://docs.rke2.io/install/ha)

### 0.4 선행조건 문서와의 경계

별도 **선행조건 문서 1.1~1.7**의 방화벽·보안팀 신청, NetworkManager, DNS, Management swap OFF, 기존 runtime 정리, 선택적 bind mount, 최종 점검을 완료한 뒤 아래 설치를 시작한다. 해당 작업은 이 문서에서 반복하지 않는다.

선택한 mount 매핑은 `/app/rke2/rancher → /var/lib/rancher` 전체다. 설치 명령은 기존 RKE2 기본 경로를 유지하며, 이때 실제 데이터는 `/app/rke2/rancher/rke2`에 저장된다. mount와 부팅 의존성은 선행조건 문서에서 관리한다.

이 문서의 0.3절은 설치에서 사용하는 L4 listener·backend와 TLS 방식의 명세다. 실제 DNS/방화벽 신청·적용은 선행조건 문서에서 수행한다. 추가 listener가 없는 환경은 6단계의 직접 IP 조인 분기를 선택한다.

## 1. MGMT-1 bootstrap 토큰 생성

**선행조건 완료 후 MGMT-1에서 시작한다.** MGMT-2/3에는 6단계에서 같은 클러스터의 토큰을 전달한다.

**MGMT-1만: 토큰을 화면에 출력하지 않고 생성. 기존 파일이 있으면 중단한다.**

```bash
#설정 폴더 생성
sudo install -d -m 700 /etc/rancher/rke2
#토큰 생성
sudo bash -c 'set -e; test ! -e /etc/rancher/rke2/server-token; umask 077; openssl rand -hex 32 > /etc/rancher/rke2/server-token'
#토큰 파일 권한 확인 600 root 이어야 함
sudo stat -c '%a %U %n' /etc/rancher/rke2/server-token
```

새 토큰 파일은 root:root 600이어야 한다. 이 short token은 최초 bootstrap용이다. 첫 기동 뒤 실제 `/var/lib/rancher/rke2/server/token`의 CA 해시가 붙은 secure token을 승인된 비밀관리 경로로 MGMT-2/3에 전달한다. 최초 short token은 CA 해시를 모르므로 trusted network에서 초기화한다. node 등록 토큰과 Rancher bootstrap 비밀번호는 서로 다르다. [공식 근거 S2](https://github.com/rancher/rke2/releases/tag/v1.36.4%2Brke2r1) [공식 근거 S4](https://docs.rke2.io/install/ha)

## 2. MGMT-1 설정 파일

**대상: MGMT-1, 같은 Bash 세션 유지.**

```bash
#rancher 도메인 입력
read -r -p 'Rancher FQDN (예: rancher.company.internal): ' RANCHER_HOST

#위의 명령어 입력시 실제 도메인을 입력하도록 되어 있음
# https://, port, / 제외하고 입력 
# ex) rancher.company.internal

#위에서 입력한 도메인 기본 형식 확인
[[ "$RANCHER_HOST" =~ ^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?$ && "$RANCHER_HOST" == *.* ]] || { echo 'FQDN 확인 필요'; exit 1; }
export RANCHER_HOST

#L4 VIP와 MGMT 3대의 IP 입력. 괄호 안은 실서버 값
read -r -p 'L4 VIP (예: 10.10.10.108): ' VIP_IP
read -r -p 'MGMT-1 IP (예: 10.10.10.109): ' MGMT1_IP
read -r -p 'MGMT-2 IP (예: 10.10.10.110): ' MGMT2_IP
read -r -p 'MGMT-3 IP (예: 10.10.10.111): ' MGMT3_IP

#IPv4 형식인지 확인. 틀린 값이 있으면 그 값을 출력하고 중단
for ip in "$VIP_IP" "$MGMT1_IP" "$MGMT2_IP" "$MGMT3_IP"; do
  [[ "$ip" =~ ^([0-9]{1,3}\.){3}[0-9]{1,3}$ ]] || { echo "IP 형식 확인 필요: '$ip'"; exit 1; }
done

#MGMT-1 IP가 이 서버에 실제로 있는 주소인지 확인. 다른 서버에서 실행했거나 오타면 중단
ip -o -4 addr show | awk '{print $4}' | cut -d/ -f1 | grep -qx "$MGMT1_IP" || { echo "이 서버에 $MGMT1_IP 주소가 없음"; exit 1; }

#기존 파일 보호차원에서 입력
sudo test ! -e /etc/rancher/rke2/config.yaml || { echo '기존 config가 있어 중단'; exit 1; }

#위 입력이 이 셸에서 끝났는지 확인. 블록 뒷부분만 붙여넣으면 변수가 비어 config가 빈 값으로 만들어짐
for v in RANCHER_HOST VIP_IP MGMT1_IP MGMT2_IP MGMT3_IP; do
  [ -n "${!v}" ] || { echo "$v 값이 비어 있음: 블록을 처음부터 다시 실행"; exit 1; }
done

#설정 파일 생성
sudo tee /etc/rancher/rke2/config.yaml >/dev/null <<EOF
node-name: mgmt-1
node-ip: ${MGMT1_IP}
token-file: /etc/rancher/rke2/server-token
tls-san:
  - ${MGMT1_IP}
  - ${MGMT2_IP}
  - ${MGMT3_IP}
  - ${VIP_IP}
  - ${RANCHER_HOST}
cni: canal
ingress-controller: traefik
selinux: true
write-kubeconfig-mode: "0600"
etcd-snapshot-schedule-cron: "0 */6 * * *"
etcd-snapshot-retention: 20
EOF

#설정 파일 권한 제한
sudo chmod 600 /etc/rancher/rke2/config.yaml
```

`token-file` 경로와 `tls-san` 등은 RKE2 server 설정이다 [공식 근거 S7](https://docs.rke2.io/reference/server_config). Rancher 웹 인증서는 8단계에서 별도로 제공한다. API SAN에 웹 FQDN을 넣었다고 웹 인증서가 생기지 않는다. `etcd-expose-metrics`는 필요 시 내부 수집 설계 후 활성화한다. snapshot cron은 노드 시간대 기준이며 UTC/KST를 기록한다. 6시간 간격 20개는 대략 5일의 **노드 로컬** 보관일 뿐 외부 백업이 아니다.

Nexus mirror가 최초 설치에 필요하면 **지금 부록A의 노드 registry 준비를 먼저 수행**한다.

## 3. MGMT Traefik HelmChartConfig

**대상: MGMT-1만.** 아래는 원하는 형태를 명시하는 구성이다. 신규 1.36에는 Traefik이 기본이며, “기본값은 무조건 클라우드용이라 온프레미스에서 멈춘다”는 원문 설명은 삭제했다. [공식 근거 S2](https://github.com/rancher/rke2/releases/tag/v1.36.4%2Brke2r1) [공식 근거 S6](https://docs.rke2.io/networking/networking_services)

```bash
#설정파일 폴더 생성
sudo install -d -m 755 /var/lib/rancher/rke2/server/manifests

# config 파일 생성
sudo tee /var/lib/rancher/rke2/server/manifests/rke2-traefik-config.yaml >/dev/null <<'YAML'
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: rke2-traefik
  namespace: kube-system
spec:
  valuesContent: |-
    deployment:
      kind: DaemonSet
    ports:
      web:
        hostPort: 80
      websecure:
        hostPort: 443
    service:
      type: ClusterIP
YAML
```

- `hostPort`는 노드 포트이고 `ports.web.port` 같은 컨테이너 entrypoint와 다르다. 컨테이너를 무작정 80/443으로 바꾸지 않는다.
- hostPort는 CNI DNAT로 구현될 수 있어 `ss -lntp`에 안 보여도 정상일 수 있다. 실제 접속으로 검증한다.
- 파일은 실행 중에도 감지·조정된다. 나중에 생성했다고 RKE2 재시작이 반드시 필요한 것은 아니다. 생성된 DaemonSet을 수동 수정하면 Helm이 되돌릴 수 있다. [공식 근거 S8](https://docs.rke2.io/add-ons/helm)
- 동일 파일을 MGMT-2/3에 수동 복제하면 AddOn 충돌·설정 불일치 위험이 있다. MGMT-1 장애 대비 원본은 외부 구성 저장소에 보관한다.
- 릴리스 페이지의 Traefik 차트 링크를 열었으나 404였다. **이 검토에서 패키지 schema·최종 렌더링을 직접 검증하지 못했다.** 5단계에서 실행 클러스터의 차트와 Pod spec으로 재확인해야 한다. class 이름도 `kubectl get ingressclass` 결과가 최종 기준이다.

## 4. RKE2 설치와 기동 (MGMT 3대 모두)

**대상: MGMT 3대 모두.** 같은 블록을 서버마다 실행하지만 실행 시점이 다르다. 무엇을 하게 될지는 그 서버의 config가 정한다.

| 서버 | 실행 시점 | `rke2-server`를 시작하면 |
|---|---|---|
| MGMT-1 | 지금. 1~3단계 뒤 | config에 `server:`가 없으므로 새 클러스터를 만든다 |
| MGMT-2, MGMT-3 | 6단계에서 config를 만든 뒤 | config의 `server:` 주소로 기존 클러스터에 조인한다 |

`/etc/rancher/rke2/config.yaml`이 없는 서버에서는 이 블록을 실행하지 않는다. config 없이 `rke2-server`가 시작되면 그 서버가 혼자 별도의 새 클러스터를 만들고, 나중에 조인하려면 그 데이터를 정리해야 한다.

### 4.1 외부 연결이 가능한 기본 RPM 경로

스크립트를 저장해 성공적으로 받은 뒤 실행한다. curl 실패와 설치를 분리한다.

```bash

#설치 스크립트 보관할 폴더 생성
mkdir -p "$HOME/rke2-install"


#설치 스크립트 다운로드
curl -fL --retry 3 https://get.rke2.io -o "$HOME/rke2-install/install.sh" || exit 1

#RKE2 설치
sudo env INSTALL_RKE2_VERSION='v1.36.4+rke2r1' INSTALL_RKE2_TYPE=server INSTALL_RKE2_METHOD=rpm sh "$HOME/rke2-install/install.sh" || exit 1

#패키지, 버전 확인
rpm -q rke2-server rke2-common rke2-selinux container-selinux
rke2 --version

#bind mount를 사용했다면 SELinux 파일 표시 정리
if mountpoint -q /var/lib/rancher; then
  sudo restorecon -RF /var/lib/rancher /var/lib/kubelet /var/log/pods || exit 1
  ls -Zd /var/lib/rancher /var/lib/kubelet /var/log/pods
fi

##RKE2 서버 실행
sudo systemctl enable --now rke2-server
```

RPM 경로는 `rke2-selinux`와 의존성을 설치한다. tar 설치는 이를 자동 설치하지 않는다. SELinux를 끄는 방법으로 우회하지 않는다. [공식 근거 S9](https://docs.rke2.io/security/selinux)

```bash
#최근 로그 100줄 확인
sudo journalctl -u rke2-server -n 100 --no-pager

#서비스 실행 여부 확인
sudo systemctl is-active rke2-server

#Kubernetes 노드 상태 확인
sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml get nodes -o wide
```

정상 조건: 설치 버전 일치, 서비스 active, 노드 목록에 이 서버가 Ready. MGMT-2·3은 조인과 이미지 다운로드로 Ready까지 몇 분 더 걸리며, 6단계 아래 확인으로 3대를 함께 본다. 시간은 이미지 다운로드와 디스크 성능에 따라 달라진다. `Waiting for etcd` 반복을 무조건 정상으로 간주하지 않는다. 지속되면 이벤트·이미지·DNS·디스크·포트를 점검한다.

### 4.2 완전 오프라인 대안 — 4.1 대신 선택

**선행 준비 없이는 실행 불가.** 연결 가능한 동일 OS/아키텍처 준비 서버에서 다음을 수집하고, 검증된 전송 경로로 **각 MGMT 노드** `/app/rke2-artifacts/`에 반입한다. [공식 근거 S10](https://docs.rke2.io/install/airgap)

- 해당 버전의 `rke2.linux-amd64.tar.gz`, 전체 `rke2-images.linux-amd64.tar.zst`, `sha256sum-amd64.txt`, 검토한 `install.sh`.
- 전체 이미지 bundle이 없으면 선택 CNI와 core 등 해당 릴리스가 요구하는 모든 split bundle을 반입한다. 파일명을 추측하지 말고 릴리스 asset 목록과 대조한다. 1.36의 core에는 Traefik이 포함된다 [공식 근거 S2](https://github.com/rancher/rke2/releases/tag/v1.36.4%2Brke2r1).
- Rocky 9용 `rke2-selinux`, `container-selinux`와 모든 RPM 의존성. 내부 서명 검증 가능한 RPM 저장소 또는 동일 OS의 `dnf download --resolve --alldeps`로 준비한다.
- Helm 바이너리, Rancher 2.15.2 차트·전체 이미지, 필요 시 cert-manager 차트·이미지, system-agent/installer 이미지와 Rancher k8s metadata. DEV 자동 provisioning은 RKE2 tar만으로 해결되지 않는다.

반입된 RPM 디렉터리를 검증 후 설치한다. 온라인 RPM 경로에서 정확한 버전 패키지가 보이지 않으면 버전·channel 저장소 보유 여부를 확인한다. 버전 고정을 제거하여 다른 버전을 설치하지 않는다. `--disablerepo='*'`는 로컬 의존성이 누락되면 실패하게 한다.

```bash
# 외부 RPM 저장소를 사용하지 않고 반입한 RPM과 의존 패키지를 설치. 실패하면 중단
sudo dnf --disablerepo='*' install -y /app/rke2-artifacts/rpms/*.rpm || exit 1
# 지정한 RPM 패키지의 설치 여부와 버전 확인. 누락되면 다음 단계로 진행하지 않음
rpm -q rke2-selinux container-selinux
# 반입 파일이 있는 디렉터리로 이동. 경로가 없으면 중단
cd /app/rke2-artifacts || exit 1
# 현재 폴더에 있는 반입 파일의 체크섬 검사. 필수 tar 파일이 모두 OK인지도 확인
sha256sum --ignore-missing -c sha256sum-amd64.txt || exit 1
# 위 결과에 바이너리 tar와 전체 이미지 tar가 모두 OK인지 직접 확인
sudo install -d -m 755 /var/lib/rancher/rke2/agent/images
# 전체 이미지 묶음을 RKE2 이미지 폴더에 복사, 권한 644 설정
sudo install -m 644 rke2-images.linux-amd64.tar.zst /var/lib/rancher/rke2/agent/images/
# 지정한 버전·설치 방식·노드 역할로 설치 스크립트 실행. 실패하면 중단
sudo env INSTALL_RKE2_VERSION='v1.36.4+rke2r1' INSTALL_RKE2_METHOD=tar INSTALL_RKE2_TYPE=server INSTALL_RKE2_ARTIFACT_PATH=/app/rke2-artifacts sh /app/rke2-artifacts/install.sh || exit 1
# 설치된 RKE2 버전이 지정한 버전과 같은지 확인
rke2 --version
# RKE2를 지금 시작하고, 재부팅 후에도 자동 실행되도록 등록
sudo systemctl enable --now rke2-server
```

체크섬 파일 자체도 신뢰 가능한 경로에서 받아야 한다. RPM 서명 검증을 해제하지 않는다. `/app` bind mount라면 이미지 저장 전에 실제 mount 여부를 확인한다. 오프라인 Rancher는 [공식 근거 S18](https://ranchermanager.docs.rancher.com/getting-started/installation-and-upgrade/air-gapped-helm-cli-install)의 이미지 수집·미러 업로드·로컬 차트 경로·`systemDefaultRegistry`·`useBundledSystemChart`를 적용해야 한다. 이 환경의 Nexus repository와 반입 목록은 미제공이므로 **완전 오프라인 전체 설치 완료를 보장하지 않는다**.

## 5. kubectl 권한과 Ingress 검증

**MGMT-1의 전용 관리자 계정.** kubeconfig는 사실상 cluster-admin 자격증명이다. 기존 파일을 무조건 덮어쓰지 않는다. [공식 근거 S11](https://docs.rke2.io/cluster_access)

```bash
# 현재 계정의 kubeconfig 폴더 생성, 해당 계정만 접근하도록 권한 700 설정
install -d -m 700 "$HOME/.kube"
# 기존 파일이 있으면 덮어쓰지 않고 메시지를 출력한 뒤 현재 셸 종료
test ! -e "$HOME/.kube/config" || { echo '기존 kubeconfig 있음: 백업/병합 후 진행'; exit 1; }
# 관리자 kubeconfig를 현재 계정 소유로 복사하고 권한 600 설정
sudo install -o "$(id -un)" -g "$(id -gn)" -m 600 /etc/rancher/rke2/rke2.yaml "$HOME/.kube/config"
# 이 터미널의 kubectl/Helm이 사용할 kubeconfig 경로 지정
export KUBECONFIG="$HOME/.kube/config"
# 현재 터미널에서 Helm·kubectl을 전체 경로 없이 실행하도록 검색 경로 추가
export PATH="$HOME/bin:/var/lib/rancher/rke2/bin:$PATH"
# 클러스터 노드의 Ready 상태·버전·내부 IP 등 확인
kubectl get nodes -o wide
# 시스템 Pod 상태와 배치 노드 확인
kubectl -n kube-system get pods -o wide
# IngressClass 목록과 실제 Traefik class 이름 확인
kubectl get ingressclass
# RKE2가 관리하는 Traefik Helm 차트 정보 확인
kubectl -n kube-system get helmchart rke2-traefik -o yaml
# Traefik 사용자 설정 리소스가 등록되었는지 YAML로 확인
kubectl -n kube-system get helmchartconfig rke2-traefik -o yaml
# Traefik DaemonSet의 배포 완료를 최대 10분 동안 대기
kubectl -n kube-system rollout status daemonset/rke2-traefik --timeout=10m
# Traefik DaemonSet의 상세 설정과 hostPort 확인
kubectl -n kube-system get daemonset rke2-traefik -o yaml
# Traefik Service가 ClusterIP 유형인지 확인
kubectl -n kube-system get svc rke2-traefik
```

정상 조건: DS desired/current/ready 일치, service ClusterIP, Pod의 `hostPort: 80`, `hostPort: 443`, class가 Traefik 컨트롤러를 가리킴. 적용 안 되면 `kubectl -n kube-system get jobs,pods`에서 helm-install 작업 로그와 events를 본다. 차트 기본값·valuesSchema는 실제 설치된 Helm release/차트 패키지와 대조한다.

위 블록의 `export PATH`는 지금 셸에서만 유효하다. 다시 접속하면 `kubectl: command not found`가 나오므로, 지금 `~/.bashrc`에 영구 저장한다. 이후 단계(7~10단계)는 새 접속에서 실행하는 경우가 많다.

```bash
# PATH를 ~/.bashrc에 저장. 이미 있으면 추가하지 않음
grep -qF '/var/lib/rancher/rke2/bin' ~/.bashrc || echo 'export PATH="$HOME/bin:/var/lib/rancher/rke2/bin:$PATH"' >> ~/.bashrc
# 지금 셸에도 적용하고 확인. kubectl 경로가 출력되어야 함
source ~/.bashrc
command -v kubectl
```

`~/.kube/config`가 kubectl의 기본 위치이므로 `KUBECONFIG`는 따로 저장하지 않아도 된다.

외부 PC kubeconfig의 server는 `https://10.10.10.108:6443`으로 수정하되 L4 listener·ACL·SAN이 준비되어야 한다. 서버 로컬의 127.0.0.1 복사본은 해당 서버 장애 때 사용할 수 없다. 인증서 갱신 후 수동 복사본도 갱신한다.

## 6. MGMT-2·MGMT-3 조인

MGMT-1의 `/var/lib/rancher/rke2/server/token`을 승인된 보안 전송 방식으로 각 노드의 `/etc/rancher/rke2/server-token`에 root:root 600으로 배치한다. 터미널 출력·채팅 전송을 피한다. 신규 노드에서 아래를 실행한다. **MGMT-2 성공 후 MGMT-3** 순서로 진행하면 문제 분리가 쉽다. “동시에 하면 반드시 etcd 충돌”이라는 단정은 하지 않는다.

```bash
# 현재 작업 중인 MGMT 노드 번호를 입력받음: MGMT-2는 2, MGMT-3은 3
read -r -p '노드 번호 (2 또는 3): ' MGMT_NO
case "$MGMT_NO" in 2|3) ;; *) echo "노드 번호는 2 또는 3: '$MGMT_NO'"; exit 1 ;; esac
# 앞에서 확정한 Rancher 도메인을 입력. https://나 포트는 넣지 않음
read -r -p 'Rancher FQDN: ' RANCHER_HOST
[[ "$RANCHER_HOST" =~ ^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?$ && "$RANCHER_HOST" == *.* ]] || { echo 'FQDN 확인 필요'; exit 1; }
# 2단계 MGMT-1과 같은 값을 입력. tls-san 목록이 세 노드에서 같아야 함
read -r -p 'L4 VIP (예: 10.10.10.108): ' VIP_IP
read -r -p 'MGMT-1 IP (예: 10.10.10.109): ' MGMT1_IP
read -r -p 'MGMT-2 IP (예: 10.10.10.110): ' MGMT2_IP
read -r -p 'MGMT-3 IP (예: 10.10.10.111): ' MGMT3_IP
# IPv4 형식인지 확인. 틀린 값이 있으면 그 값을 출력하고 중단
for ip in "$VIP_IP" "$MGMT1_IP" "$MGMT2_IP" "$MGMT3_IP"; do
  [[ "$ip" =~ ^([0-9]{1,3}\.){3}[0-9]{1,3}$ ]] || { echo "IP 형식 확인 필요: '$ip'"; exit 1; }
done
# 노드 번호에 맞는 IP를 이 노드의 IP로 선택
if [ "$MGMT_NO" = 2 ]; then MGMT_IP=$MGMT2_IP; else MGMT_IP=$MGMT3_IP; fi
# 그 IP가 이 서버에 실제로 있는지 확인. 번호를 잘못 넣었거나 다른 서버면 중단
ip -o -4 addr show | awk '{print $4}' | cut -d/ -f1 | grep -qx "$MGMT_IP" || { echo "이 서버에 $MGMT_IP 주소가 없음: 노드 번호 확인"; exit 1; }
# 새 노드가 합류할 기존 클러스터의 등록 주소를 입력
read -r -p "9345 조인 주소 (L4 9345 준비 시 VIP ${VIP_IP}, 아니면 MGMT-1 ${MGMT1_IP}): " JOIN_ADDR
# 등록 주소가 위에서 입력한 VIP 또는 MGMT-1 주소인지 검사
case "$JOIN_ADDR" in "$VIP_IP"|"$MGMT1_IP") ;; *) echo "조인 주소는 $VIP_IP 또는 $MGMT1_IP: '$JOIN_ADDR'"; exit 1 ;; esac
# 조인 주소의 9345 포트가 열려 있는지 확인. 실패하면 L4·방화벽·MGMT-1 기동 상태 점검
timeout 5 bash -c "</dev/tcp/${JOIN_ADDR}/9345" || { echo "${JOIN_ADDR}:9345 연결 안 됨"; exit 1; }
# 사전에 보안 전송한 토큰 파일이 존재하고 비어 있지 않은지 확인
sudo test -s /etc/rancher/rke2/server-token || { echo '/etc/rancher/rke2/server-token 없음: 토큰 먼저 배치'; exit 1; }
# 클러스터 합류용 토큰 파일을 root만 읽고 쓸 수 있도록 제한
sudo chmod 600 /etc/rancher/rke2/server-token
# 위 입력이 이 셸에서 끝났는지 확인. 블록 뒷부분만 붙여넣으면 변수가 비어 config가 빈 값으로 만들어짐
for v in MGMT_NO MGMT_IP JOIN_ADDR RANCHER_HOST VIP_IP MGMT1_IP MGMT2_IP MGMT3_IP; do
  [ -n "${!v}" ] || { echo "$v 값이 비어 있음: 블록을 처음부터 다시 실행"; exit 1; }
done
# 기존 RKE2 설정이 있으면 덮어쓰지 않고 현재 셸 종료
sudo test ! -e /etc/rancher/rke2/config.yaml || { echo '기존 설정 있음'; exit 1; }
# EOF 전까지의 내용을 RKE2 설정 파일로 저장. 변수는 실제 입력값으로 치환
sudo tee /etc/rancher/rke2/config.yaml >/dev/null <<EOF
server: https://${JOIN_ADDR}:9345
node-name: mgmt-${MGMT_NO}
node-ip: ${MGMT_IP}
token-file: /etc/rancher/rke2/server-token
tls-san:
  - ${MGMT1_IP}
  - ${MGMT2_IP}
  - ${MGMT3_IP}
  - ${VIP_IP}
  - ${RANCHER_HOST}
cni: canal
ingress-controller: traefik
selinux: true
write-kubeconfig-mode: "0600"
etcd-snapshot-schedule-cron: "0 */6 * * *"
etcd-snapshot-retention: 20
EOF
# RKE2 설정 파일을 root만 읽고 쓸 수 있도록 제한
sudo chmod 600 /etc/rancher/rke2/config.yaml
```

config를 만든 노드에서 이어서 **4.1(오프라인이면 4.2) 블록 전체**를 실행한다. 설치 스크립트 다운로드부터 `systemctl enable --now rke2-server`까지이며, 마지막 명령이 실행되는 순간 조인이 시작된다. 1~3단계(토큰 생성, MGMT-1 config, Traefik 설정)는 반복하지 않는다. MGMT-2를 끝낸 뒤 MGMT-3에서 같은 순서(6단계 config → 4.1)를 반복하고, MGMT-1에서 다음을 확인한다.

```bash
# 클러스터 노드의 Ready 상태·버전·내부 IP 등 확인
kubectl get nodes -o wide
# etcd Pod가 각 MGMT 노드에 정상 배치되어 실행 중인지 확인
kubectl -n kube-system get pods -l component=etcd -o wide
# Traefik DaemonSet의 DESIRED/CURRENT/READY 개수 확인
kubectl -n kube-system get ds rke2-traefik
# 시스템 Pod 상태와 배치 노드 확인
kubectl -n kube-system get pods -o wide
```

3대 Ready, etcd 3개, Traefik 3개가 기준이다. 109로 직접 등록해도 기존 클러스터가 109 단독 의존으로 바뀌지는 않는다. 다만 **109 장애 중 신규/복구 노드의 최초 접속은 실패할 수 있다**. VIP 또는 생존 server의 등록 주소를 사용한다. RKE2 HA는 고정 등록 엔드포인트를 권장한다 [공식 근거 S4](https://docs.rke2.io/install/ha).

## 7. Helm과 버전 고정 차트 준비

**MGMT-1.** 원문의 Helm 3.19 대신 Kubernetes 1.36을 지원하는 3.21/3.22 계열 중 승인된 정확한 패치를 선택한다. 최신 패치와 Rancher의 실제 동작 조합은 이 검토에서 확정하지 않았다. [공식 근거 S12](https://helm.sh/docs/v3/topics/version_skew/)

```bash
# 설치할 Helm의 정확한 패치 버전을 입력
read -r -p '승인된 Helm 버전 (실재하는 v3.21.x 또는 v3.22.x 패치): ' HELM_VERSION
# Helm 버전 문자열이 지정한 계열의 형식인지 검사. 실제 배포 여부는 다운로드로 확인
[[ "$HELM_VERSION" =~ ^v3\.(21|22)\.[0-9]+$ ]] || exit 1
# 이 서버의 CPU 종류를 Helm 파일 이름 형식으로 변환. 실서버 x86_64 → amd64, Apple Silicon 실습 VM aarch64 → arm64
case "$(uname -m)" in
  x86_64)  HELM_ARCH=amd64 ;;
  aarch64) HELM_ARCH=arm64 ;;
  *) echo "지원하지 않는 CPU 종류: $(uname -m)"; exit 1 ;;
esac
# Helm 다운로드·압축 해제에 사용할 임시 디렉터리 생성
HELM_TMP=$(mktemp -d)
# 선택한 버전, 이 서버 CPU 종류의 Helm 압축 파일 다운로드
curl -fL "https://get.helm.sh/helm-${HELM_VERSION}-linux-${HELM_ARCH}.tar.gz" -o "$HELM_TMP/helm.tgz" || exit 1
# 같은 버전의 공식 체크섬 파일 다운로드
curl -fL "https://get.helm.sh/helm-${HELM_VERSION}-linux-${HELM_ARCH}.tar.gz.sha256sum" -o "$HELM_TMP/sha256sum" || exit 1
# 체크섬 파일 첫 줄에서 예상 SHA-256 해시값을 추출
EXPECTED_SHA=$(awk 'NR==1 {print $1}' "$HELM_TMP/sha256sum")
# 다운로드한 Helm 압축 파일의 SHA-256을 예상값과 비교. 불일치하면 종료
printf '%s  %s\n' "$EXPECTED_SHA" "$HELM_TMP/helm.tgz" | sha256sum -c - || exit 1
# 검증한 Helm 압축 파일을 임시 디렉터리에 해제
tar -xzf "$HELM_TMP/helm.tgz" -C "$HELM_TMP" || exit 1
# 현재 계정의 실행 파일 보관 폴더 생성
install -d -m 755 "$HOME/bin"
# Helm 실행 파일을 사용자 bin 폴더에 복사하고 실행 권한 부여
install -m 755 "$HELM_TMP/linux-${HELM_ARCH}/helm" "$HOME/bin/helm"
# 현재 터미널에서 Helm·kubectl을 전체 경로 없이 실행하도록 검색 경로 추가
export PATH="$HOME/bin:/var/lib/rancher/rke2/bin:$PATH"
# 현재 실행되는 Helm 버전 확인
helm version --short
# Rancher stable Helm 차트 저장소 등록
helm repo add rancher-stable https://releases.rancher.com/server-charts/stable
# 등록된 Helm 저장소의 차트 목록 갱신. 실패하면 종료
helm repo update || exit 1
# Rancher 차트·설정 보관 폴더를 현재 계정만 접근 가능하게 생성
install -d -m 700 "$HOME/rancher-install"
# Rancher 2.15.2 차트 패키지를 내려받아 로컬 폴더에 보관
helm pull rancher-stable/rancher --version 2.15.2 --destination "$HOME/rancher-install" || exit 1
# 받은 Rancher 차트의 version/appVersion 등 메타데이터 확인
helm show chart "$HOME/rancher-install/rancher-2.15.2.tgz"
# 차트의 기본 설정값을 참고 파일로 저장. 이 명령은 설치하지 않음
helm show values "$HOME/rancher-install/rancher-2.15.2.tgz" > "$HOME/rancher-install/rancher-default-values.yaml"
```

차트 취득 실패 시 latest로 바꾸지 않는다. version/appVersion, 취득 출처, SHA-256, 승인일을 기록한다. 오프라인에서는 검증된 파일을 반입한다.

## 8. Rancher TLS 방식과 cert-manager

### 8.1 기본 경로: 준비된 사내 CA 서버 인증서 사용

원문의 Rancher 자체 발급 방식 대신 **사내 CA 서버 인증서 반입 방식**을 기본 예제로 사용한다. 환경별 선택이며 필수 사양은 아니다. 이 방식은 cert-manager가 필요 없다. 브라우저·DEV OS·필요한 Pod의 CA 신뢰도 확인한다. [공식 근거 S14](https://ranchermanager.docs.rancher.com/getting-started/installation-and-upgrade/install-upgrade-on-a-kubernetes-cluster/)

다음 파일 3개를 MGMT-1의 보호된 경로에 준비한다.

| 파일            | 내용                                          |
| ------------- | ------------------------------------------- |
| `tls.crt`     | FQDN SAN을 가진 서버 인증서, 이어서 중간 CA를 올바른 순서로 포함  |
| `tls.key`     | 대응하는 개인키, 권한 600                            |
| `cacerts.pem` | Rancher agent가 신뢰할 CA bundle. 서버 인증서 자체가 아님 |

```bash
# tls.crt, tls.key, cacerts.pem을 준비한 디렉터리의 절대 경로 입력
read -r -p '인증서 디렉터리 절대 경로: ' TLS_DIR
# 서버 인증서·개인키·CA 파일이 모두 존재하고 비어 있지 않은지 검사
test -s "$TLS_DIR/tls.crt" && test -s "$TLS_DIR/tls.key" && test -s "$TLS_DIR/cacerts.pem" || exit 1
# 서버 인증서의 주체·발급자·유효기간·SAN 확인
openssl x509 -in "$TLS_DIR/tls.crt" -noout -subject -issuer -dates -ext subjectAltName
# 인증서에서 공개키를 추출해 SHA-256 계산. 다음 개인키의 공개키 해시와 비교
openssl x509 -in "$TLS_DIR/tls.crt" -pubkey -noout | openssl pkey -pubin -outform DER | sha256sum
# 개인키의 공개키를 추출해 SHA-256 계산. 인증서 쪽 해시와 같아야 함
openssl pkey -in "$TLS_DIR/tls.key" -pubout -outform DER | sha256sum
# 위 두 해시가 일치하는지 확인
kubectl create namespace cattle-system --dry-run=client -o yaml | kubectl apply -f -
# 준비한 서버 인증서와 개인키를 Rancher HTTPS용 Secret으로 저장
kubectl -n cattle-system create secret tls tls-rancher-ingress --cert="$TLS_DIR/tls.crt" --key="$TLS_DIR/tls.key"
# Rancher가 배포할 사내 CA bundle을 tls-ca Secret으로 저장
kubectl -n cattle-system create secret generic tls-ca --from-file=cacerts.pem="$TLS_DIR/cacerts.pem"
```

두 해시, SAN, 유효기간, CA 체인 검증을 마친 뒤 진행한다. 기존 Secret이 있으면 내용을 확인하여 갱신 방법을 결정한다. 무조건 삭제 후 재생성하지 않는다.

### 8.2 대안: Rancher 발행 인증서 + cert-manager

원문의 인증서 방식을 유지하려면 이 분기를 선택하고 8.1은 수행하지 않는다.

- upstream 지원표에서 cert-manager **1.21 계열은 Kubernetes 1.36 대응**, 1.20은 1.35까지다. 정확한 패치와 Rancher 2.15.2 권장 조합은 별도 대조해야 한다. upstream 지원을 SUSE 인증으로 해석하지 않는다. [공식 근거 S13](https://cert-manager.io/docs/releases/)
- 버전을 생략하지 않는다. `crds.enabled=true`는 선택한 차트의 values에서 확인한다.

```bash
# cert-manager 차트 저장소 등록. 8.2 대안 선택 시에만 실행
helm repo add jetstack https://charts.jetstack.io
# 등록된 Helm 저장소의 차트 목록 갱신. 실패하면 종료
helm repo update || exit 1
# 설치 가능한 cert-manager 버전 목록 중 앞의 12줄 표시
helm search repo jetstack/cert-manager --versions | head -n 12
# 검토·승인한 cert-manager의 정확한 패치 버전 입력
read -r -p '승인된 cert-manager 버전 (실재하는 v1.21.x): ' CM_VERSION
# cert-manager 버전이 지정한 계열의 문자열 형식인지 확인
[[ "$CM_VERSION" =~ ^v1\.21\.[0-9]+$ ]] || exit 1
# 선택한 cert-manager 차트가 조회되는지 메타데이터 확인
helm show chart jetstack/cert-manager --version "$CM_VERSION" || exit 1
# cert-manager와 CRD 설치, 준비 완료를 최대 10분 대기. 실패하면 종료
helm install cert-manager jetstack/cert-manager --version "$CM_VERSION" --namespace cert-manager --create-namespace --set crds.enabled=true --wait --timeout 10m || exit 1
# cert-manager 구성 Pod의 상태 확인
kubectl -n cert-manager get pods
```

9단계 values의 `ingress.tls.source`를 `rancher`로 변경하고 `privateCA: true` 행을 제거한다. 발급 CA의 Rancher 배포와 agent 접속을 확인한다. 공개 HTTP-01 Let’s Encrypt는 내부 전용 DNS에서 자동으로 동작하지 않는다.

> [!warning] cert-manager 복구
> 설치 실패 시 namespace, Helm release, events, webhook과 기존 CRD 소유 관계부터 확인한다. 원문의 CRD 일괄 삭제 명령은 사용하지 않는다. Certificate/Issuer 등 기존 리소스를 잃을 수 있다.

## 9. Rancher 2.15.2 설치

**MGMT-1, 8.1의 사내 CA 방식 예제.** Rancher FQDN은 2단계와 같은 값을 입력한다.

```bash
# 2단계와 같은 Rancher 도메인 입력. https://나 포트는 넣지 않음
read -r -p 'Rancher FQDN: ' RANCHER_HOST
[[ "$RANCHER_HOST" =~ ^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?$ && "$RANCHER_HOST" == *.* ]] || { echo "FQDN 확인 필요: '$RANCHER_HOST'"; exit 1; }
# 8.1 Secret 2개가 준비됐는지 확인. 없으면 Rancher가 인증서 없이 뜸
kubectl -n cattle-system get secret tls-rancher-ingress tls-ca >/dev/null || { echo '8.1의 Secret이 없음: 8.1 먼저'; exit 1; }
# 같은 이름의 release가 이미 있으면 중단. 실패한 첫 설치는 아래 안내대로 정리한 뒤 다시 실행
! helm status rancher -n cattle-system >/dev/null 2>&1 || { echo 'rancher release가 이미 있음: helm list -n cattle-system -a 확인'; exit 1; }
# 이후 생성하는 설정 파일을 현재 계정만 접근 가능하도록 기본 권한 제한
umask 077
# EOF 전까지를 Rancher 설치 설정 파일로 저장. 도메인 변수를 치환하며 기존 파일은 덮어씀
cat > "$HOME/rancher-install/values.yaml" <<EOF
hostname: ${RANCHER_HOST}
replicas: 3
antiAffinity: required
networkExposure:
  type: ingress
ingress:
  ingressClassName: traefik
  tls:
    source: secret
privateCA: true
agentTLSMode: strict
EOF
# 설정값으로 생성될 Kubernetes YAML을 파일로 미리 출력. 클러스터에는 적용하지 않음
helm template rancher "$HOME/rancher-install/rancher-2.15.2.tgz" --namespace cattle-system -f "$HOME/rancher-install/values.yaml" > "$HOME/rancher-install/rendered.yaml" || exit 1
# 로컬 차트와 values로 Rancher 설치, 준비 완료를 최대 15분 대기
helm install rancher "$HOME/rancher-install/rancher-2.15.2.tgz" --namespace cattle-system -f "$HOME/rancher-install/values.yaml" --wait --timeout 15m || exit 1
# Rancher Deployment 배포 완료를 최대 10분 대기
kubectl -n cattle-system rollout status deployment/rancher --timeout=10m
# Rancher Pod의 상태와 배치된 MGMT 노드 확인
kubectl -n cattle-system get pods -o wide
# Rancher Ingress의 도메인·IngressClass·TLS 설정 확인
kubectl -n cattle-system get ingress rancher -o yaml
```

첫 설치가 실패해 `helm list -n cattle-system -a`에 `failed`로 남았을 때는, values를 고친 뒤 같은 차트로 `helm upgrade rancher <차트> -n cattle-system -f <values> --wait --timeout 15m`을 실행한다. Helm이 실패해도 Rancher Pod는 뜰 수 있고, 뜨는 즉시 CRD와 `cattle-*`, `fleet-*` namespace를 만들기 시작한다. 이 상태에서 `helm uninstall`을 하면 그 리소스가 남은 채 Rancher만 지워지므로 하지 않는다. 먼저 `--dry-run=server`로 upgrade가 받아들여지는지 확인하면 안전하다.

IngressClass 이름은 5단계의 실제 값에 맞춘다. `antiAffinity: required`는 3개 노드에 배치 가능할 때 사용한다. replicas=3만으로 각 노드에 1개씩 배치됨을 보장하지 않는다. taint·자원 부족으로 Pending이면 원인을 해결한다. 차트 키는 2.15.2 소스와 실제 패키지를 대조한다 [공식 근거 S15](https://raw.githubusercontent.com/rancher/rancher/v2.15.2/chart/values.yaml).

bootstrapPassword는 지정하지 않고 **차트가 임의 생성하도록 둔다**. 명령줄에 비밀번호를 넣으면 history/프로세스 인수에 남을 수 있다. 생성값도 Kubernetes Secret/Helm release에 저장되므로 RBAC를 제한한다. 첫 로그인할 때만 관리 단말에서 다음을 수행한다.

```bash
# 최초 로그인용 비밀번호를 복호화하여 화면에 표시. 화면 공유·기록에 주의
kubectl -n cattle-system get secret bootstrap-secret -o jsonpath='{.data.bootstrapPassword}' | base64 --decode
# 직전 출력 뒤에 줄바꿈 추가
printf '\n'
```

이 명령은 의도적으로 비밀값을 화면에 표시한다. 화면 공유·기록 없이 취급하고, 첫 설정에서 길고 고유한 관리자 비밀번호로 변경한다. 취득 실패 시 기존 Rancher에 재설치를 시도하지 않는다.

## 10. Rancher 첫 로그인과 L4 검증

1. 관리 PC에서 `https://rancher.<실제도메인>`에 접속하여 CA 신뢰와 인증서 오류가 없는지 확인한다.
2. admin과 생성된 bootstrap 값으로 로그인하여 관리자 비밀번호와 Server URL을 확정한다.
3. Server URL은 DEV에서도 접근할 수 있는 같은 FQDN이어야 한다. localhost나 임시 IP를 등록하지 않는다.
4. local 클러스터 Active, Rancher 3Pod가 서로 다른 노드에 배치되었는지 확인한다.

MGMT-1 또는 승인된 관리 단말에서 사내 CA bundle로 검증한다.

```bash
# 2단계와 같은 Rancher 도메인, 8.1과 같은 인증서 디렉터리 입력. 새 셸에서는 이전 값이 남아 있지 않음
read -r -p 'Rancher FQDN: ' RANCHER_HOST
read -r -p '인증서 디렉터리 절대 경로 (8.1과 같은 값): ' TLS_DIR
test -s "$TLS_DIR/cacerts.pem" || { echo "$TLS_DIR/cacerts.pem 없음: 경로 확인"; exit 1; }
# 지정한 CA로 HTTPS 인증서를 검증하면서 Rancher /ping 응답 확인
curl --fail --cacert "$TLS_DIR/cacerts.pem" "https://${RANCHER_HOST}/ping"; echo
# MGMT 노드 IP 3개를 공백으로 구분해 입력 (예: 10.10.10.109 10.10.10.110 10.10.10.111)
read -r -p 'MGMT IP 3개: ' -a MGMT_IPS
# 세 MGMT 노드 IP를 차례로 선택해 아래 직접 접속 검사를 반복
for addr in "${MGMT_IPS[@]}"; do
  # 지정한 CA로 HTTPS 인증서를 검증하면서 Rancher /ping 응답 확인
  curl --fail --cacert "$TLS_DIR/cacerts.pem" --resolve "${RANCHER_HOST}:443:${addr}" "https://${RANCHER_HOST}/ping" || break
  echo " ← ${addr}"
done
```

각 요청에서 pong 응답을 확인한다. curl -k를 영구 해결책으로 사용하지 않는다. DEV에서도 OS CA 신뢰 반영 후 검증한다. RKE2 API CA와 Rancher CA는 별개다.

## 부록A. Nexus registry mirror·인증

### A.1 서로 다른 설정 구분

| 설정 | 대상 |
|---|---|
| containerd registries.yaml / Rancher cluster Registries | 노드 system image 취득·upstream mirror |
| namespace의 Registry Secret/imagePullSecrets | 앱 Pod의 private image 인증 |
| Apps Chart Repository | Helm index/차트 취득. Docker mirror 설정과 별개 |

Nexus Docker connector의 host:port를 사용한다. 일반 Web UI 경로를 endpoint로 넣어도 Docker Registry로 작동하는 것은 아니다. Docker Hub용 proxy가 quay.io 등 다른 registry까지 대체하지 않는다. 저장 경로·proxy/hosted/group·인증 realm·CA를 Nexus 관리자와 확인한다.

원문의 mirror key를 Nexus 자기 주소로 두는 구성은 **이미 image 이름이 Nexus호스트:5000/path:tag인 경우**에만 그 주소의 endpoint 선택에 영향을 준다. docker.io/rancher/... image를 Nexus로 보내려면 mirror key는 docker.io여야 한다. 같은 주소로 바꾸기만 하면 모든 upstream이 대체된다는 해석은 잘못이다.

### A.2 MGMT 전체 노드, 첫 기동 전

아래는 **구조 템플릿**이다. 실제 endpoint를 확인하여 root 전용 편집기로 저장한다. 비밀값이 포함되므로 완성된 YAML을 Obsidian에 복사하지 않는다. [공식 근거 S20](https://docs.rke2.io/install/private_registry)

```yaml
# /etc/rancher/rke2/registries.yaml — REPLACE_* 값을 모두 교체
mirrors:
  docker.io:
    endpoint:
      - "https://REPLACE_DOCKER_PROXY_HOST:REPLACE_PORT"
configs:
  "REPLACE_DOCKER_PROXY_HOST:REPLACE_PORT":
    auth:
      username: "REPLACE_PULL_ONLY_USER"
      password: "REPLACE_PASSWORD"
    tls:
      ca_file: /etc/rancher/rke2/nexus-ca.crt
```

```bash
# RKE2 설정 폴더 생성, root만 접근하도록 권한 700 설정
sudo install -d -m 700 /etc/rancher/rke2
# root 권한으로 registry 설정 파일을 편집. 실제 endpoint·인증·CA를 입력
sudoedit /etc/rancher/rke2/registries.yaml
# registry 인증이 포함된 파일을 root만 읽고 쓰도록 제한
sudo chmod 600 /etc/rancher/rke2/registries.yaml
# 진위를 확인한 CA 파일도 위 ca_file 경로에 배치
sudo test -s /etc/rancher/rke2/nexus-ca.crt
```

docker.io 외 registry.k8s.io, quay.io 등은 실제 image 목록에서 추출하고, 각각을 처리할 수 있는 Nexus proxy/hosted와 mirror를 추가한다. 저장 경로를 바꿨다면 정확한 rewrite를 검증한다.

HTTP registry는 endpoint에 http://HOST:PORT를 명시한다. insecure_skip_verify는 HTTPS 인증서 검증 생략 옵션이며 HTTP로 전환하는 옵션이 아니다. 표준 예제는 사내 CA를 사용하는 HTTPS다. 원문의 HTTP:5000 사용 시 격리망 정책과 평문 인증 전송을 확인한다.

외부 fallback 금지가 필요하면 RKE2 config에 disable-default-registry-endpoint: true를 설정한다. 이는 **mirror에 명시한 registry에만 적용**된다. 나머지 외부 접근은 ACL로도 통제한다. [공식 근거 S20](https://docs.rke2.io/install/private_registry)

기존 노드의 설정을 바꾸면 한 대씩 재시작한 뒤 실제 pull로 확인한다. ctr pull은 CRI 설정과 다르게 동작할 수 있으므로 동봉된 crictl을 사용한다.

```bash
# Nexus에서 준비한 테스트 이미지의 정확한 주소와 태그 입력
read -r -p 'Nexus에 준비한 테스트 image의 정확한 이름: ' TEST_IMAGE
# RKE2 containerd의 CRI 경로를 통해 실제 이미지 다운로드 검사
sudo /var/lib/rancher/rke2/bin/crictl --runtime-endpoint unix:///run/k3s/containerd/containerd.sock pull "$TEST_IMAGE"
# containerd 최근 로그 100줄로 이미지 취득 오류 확인
sudo tail -n 100 /var/lib/rancher/rke2/agent/containerd/containerd.log
```

upstream 이름으로 image를 pull하고 Nexus access log와 대조한다. 기존 cache만으로 성공을 판정하지 않는다. 테스트 목적으로 운영 중 system image를 삭제하지 않는다.

DEV/STAGE의 registry 설정은 [클러스터 설치 문서](02_DEV_STAGE_클러스터_설치.md)를 따른다.

### B.1 etcd 클러스터 확인

MGMT 3대가 하나의 etcd 클러스터로 묶여 있는지 확인한다. `kubectl get nodes`에 3대가 보이는 것만으로는 etcd 복제 상태를 알 수 없다.

**대상: MGMT 아무 노드.** 조회를 지금 접속한 노드의 etcd Pod에서 실행하므로, 다른 MGMT를 끈 장애 시험 중에도 살아 있는 노드에서 그대로 쓸 수 있다. etcd 이미지에는 셸이 없어서 `etcdctl`을 직접 호출한다.

```bash
# 이 서버의 노드 이름. etcd Pod 이름은 etcd-<노드 이름>
NODE=$(sudo awk '/^node-name:/ {print $2}' /etc/rancher/rke2/config.yaml)
[ -n "$NODE" ] || { echo 'config.yaml에서 node-name을 찾지 못함'; exit 1; }
# etcd 역할 노드의 내부 IP로 endpoint 목록 생성
EP=$(kubectl get nodes -l node-role.kubernetes.io/etcd=true -o jsonpath='{range .items[*]}{.status.addresses[?(@.type=="InternalIP")].address}{"\n"}{end}' | sed 's|.*|https://&:2379|' | paste -sd, -)
echo "$EP"
# RKE2가 만든 etcd 클라이언트 인증서로 etcdctl 실행하는 함수
T=/var/lib/rancher/rke2/server/tls/etcd
etcdq() { kubectl -n kube-system exec "etcd-${NODE}" -- etcdctl --cacert=$T/server-ca.crt --cert=$T/server-client.crt --key=$T/server-client.key "$@"; }
# 멤버 목록: 클러스터에 묶인 etcd
etcdq member list -w table
# 멤버별 리더 여부와 복제 위치
etcdq --endpoints="$EP" endpoint status -w table
# 멤버별 쓰기 응답
etcdq --endpoints="$EP" endpoint health
```

| 결과 | 정상 기준 | 의미 |
|---|---|---|
| `member list` | 3개, 모두 `started`, `IS LEARNER`가 모두 `false` | 세 etcd가 하나의 데이터베이스를 운영한다. 셋 다 투표권이 있어 1대가 죽어도 과반이 유지된다 |
| `endpoint status`의 IS LEADER | 정확히 1개만 `true` | 리더가 하나로 정해져 있다 |
| `endpoint status`의 RAFT TERM | 3개가 같음 | 같은 선거 회차를 보고 있다 |
| `endpoint status`의 RAFT INDEX | 3개가 같거나 차이가 아주 작음 | 데이터가 같은 지점까지 복제돼 있다. 차이가 계속 벌어지면 뒤처진 노드의 디스크와 네트워크를 본다 |
| `endpoint health` | 3개 모두 `healthy` | 쓰기 요청에 응답한다. `took`이 수백 ms 이상이면 디스크 지연을 의심한다 |

장애 시험(아래 체크리스트의 MGMT-1 계획 중단)에서는 MGMT-1을 끈 상태로 MGMT-2에서 이 블록을 실행한다. 정상이면 MGMT-1 endpoint만 실패하고, 나머지 2개가 `healthy`이며, 리더가 MGMT-2나 MGMT-3으로 넘어가 있다. MGMT-1 복귀 후 다시 실행해 3개 모두 `healthy`인지 확인한다.

### B.2 수용 체크리스트

### D.1 저장 대상

| 대상 | 보관·복원의 목적 |
|---|---|
| MGMT/DEV etcd snapshot | 각각의 클러스터 상태, 별도 관리 |
| snapshot 시점 server/token | bootstrap 암호화 데이터 복호화. snapshot과 대응시켜 보관 |
| /etc/rancher/rke2, manifests 원본, values/차트 | 노드 외부 설정 재구성 |
| 인증서/개인키/CA/Nexus CA | TLS와 신뢰 구성 복구 |
| Rancher Backup Operator 외부 백업 | Rancher 리소스 이전·복구, etcd 백업과 목적 구분 |
| 앱 DB/PV/외부 스토리지 | etcd snapshot에 들어 있지 않은 데이터 |
| Nexus blob/config/DB, L4/DNS 설정 | image 재취득과 진입점 복구 |

```bash
# 현재 etcd의 수동 스냅샷 생성. 변경 전 백업용 이름 지정
sudo rke2 etcd-snapshot save --name pre-change
# RKE2가 인식하는 etcd 스냅샷 목록 확인
sudo rke2 etcd-snapshot ls
```

rke2가 PATH에 없으면 RPM 설치는 /usr/bin/rke2, tar 설치는 /usr/local/bin/rke2를 확인한다. snapshot과 token을 암호화·접근 제한하여 외부에 저장한다. S3 호환 저장소도 CA/자격증명/retention을 구성하고 실제 복원까지 시험한다. 로컬 cron 성공만으로 DR이 완료되지 않는다. [공식 근거 S21](https://docs.rke2.io/datastore/backup_restore)

### D.2 MGMT quorum 상실 시 복원 예제

> [!danger] 장애 복원 전용. 일반 설치나 단일 노드 장애에 실행하지 않는다.
> snapshot 시점 이후의 etcd 변경은 잃는다. 전체 server를 중단·격리하고 대상 클러스터, snapshot 진위, 원래 token, 버전, 마운트를 확인한다. 기존 클러스터와 복원본을 동시에 운영하지 않는다. 아래는 같은 호스트의 로컬 snapshot 복원 예제다.

모든 MGMT 노드에서 중단한다.

```bash
# 재해복구 절차에서만 실행: 이 노드의 RKE2 server 중지
sudo systemctl stop rke2-server
```

MGMT-1에서만 복원한다. 기존 token 파일을 유지한다. 신규 호스트는 원래 token을 먼저 배치하고 이름/IP/SAN/기존 Node 정리를 별도 계획한다.

```bash
# 복원에 사용할 검증된 로컬 스냅샷의 절대 경로 입력
read -r -p '검증된 로컬 snapshot 절대 경로: ' RESTORE_SNAPSHOT
# 복원 파일이 존재하고 비어 있지 않은지 확인. 백업의 진위·정합성 검증은 별도 필요
sudo test -s "$RESTORE_SNAPSHOT" || exit 1
# 재해복구 전용: 지정 스냅샷으로 etcd를 복원하고 멤버 구성을 초기화. 로컬 파일 사용
sudo rke2 server --cluster-reset --cluster-reset-restore-path="$RESTORE_SNAPSHOT" --etcd-s3=false
```

reset 완료 메시지를 확인한 뒤 MGMT-1을 정상 기동한다. reset 옵션을 상시 config에 추가하지 않는다.

```bash
# 재해복구 절차의 확인을 마친 뒤 RKE2 server를 정상 모드로 시작
sudo systemctl start rke2-server
```

MGMT-2/3은 중단 상태로 유지하고 peer의 오래된 etcd DB만 옮겨 보관한다. 전체 data-dir을 지우지 않는다. 디스크와 bind mount 경계를 먼저 확인한다.

```bash
# MGMT-2, 다음 MGMT-3에서 실행. MGMT-1에서 실행 금지
sudo test -d /var/lib/rancher/rke2/server/db || exit 1
# MGMT-2/3 전용: 기존 etcd DB를 시간표시가 붙은 이름으로 이동해 보관
sudo mv /var/lib/rancher/rke2/server/db "/var/lib/rancher/rke2/server/db.pre-restore.$(date +%Y%m%d%H%M%S)"
# 재해복구 절차의 확인을 마친 뒤 RKE2 server를 정상 모드로 시작
sudo systemctl start rke2-server
```

MGMT-2 재join을 확인한 뒤 MGMT-3을 처리한다. 필요하면 server 등록 주소를 복구된 MGMT-1로 설정하고 VIP가 미복구 노드로 전달하지 않게 조정한다. 3대 Ready, etcd health, Rancher/DEV agent와 앱 정합성을 확인한다. Rancher 관리 DEV는 이 직접 편집 예제를 그대로 쓰지 말고 Rancher snapshot restore 및 agent plan과 함께 검증한다.

### D.3 복원 훈련의 성공 조건

- [ ] 외부망 없이 필요한 image/차트/패키지 취득 가능
- [ ] API/Rancher/DEV/PV/DB 정합성 복구
- [ ] 실측 RPO/RTO, 담당자, 연락처, token 보관 위치를 보호된 운영대장에 기록
