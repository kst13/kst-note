# 클러스터 만들기 — 로컬 k3d, 실서버 RKE2

구성 배경(server/agent, 규모별 구성)은 [[구성도]], k3d 설치와 옵션은 [[설치(k3d)]] 참고.

| 절 | 대상 |
| --- | --- |
| lab, lab3 | 로컬 k3d. 학습·리허설 |
| 실서버 RKE2 3대 겸임 | 운영. lab3 를 실제 머신으로 옮긴 형태 |

## 로컬에서 쓰는 클러스터 두 개

| 이름 | 구성 | 목적 | API 포트 | Ingress 포트 |
| --- | --- | --- | --- | --- |
| `lab` | server 1 + agent 2 | 역할 구분, Pod 분산, 앱 배포 실습 | 61118 | 8081 / 8443 |
| `lab3` | server 3 + agent 0 | 실서버 3대 겸임 흉내. etcd 과반, 노드 장애 리허설 | 61119 | 8082 / 8444 |

- 포트를 다르게 잡아 두 클러스터를 동시에 둘 수 있음. 8080은 다른 로컬 앱이 쓰므로 피함
- 노드 컨테이너가 합쳐서 6개라 메모리를 봐 가며 한쪽은 `k3d cluster stop`으로 재워 둠
- 전환: `kubectl config use-context k3d-lab` / `k3d-lab3`

## lab — server 1 + agent 2

### 명령 한 줄

```bash
k3d cluster create lab \
  --servers 1 \
  --agents 2 \
  --image rancher/k3s:v1.35.5-k3s1 \
  --api-port 127.0.0.1:61118 \
  -p "8081:80@loadbalancer" \
  -p "8443:443@loadbalancer"
```

### 설정 파일

```yaml
# k3d-lab.yaml
apiVersion: k3d.io/v1alpha5
kind: Simple
metadata:
  name: lab
servers: 1                          # 컨트롤 플레인 1개
agents: 2                           # 워커 2개
image: rancher/k3s:v1.35.5-k3s1     # k3s 버전 고정 (Rancher 지원 범위 1.33~1.35 안)
kubeAPI:
  hostIP: "127.0.0.1"               # API 는 로컬 PC 에서만
  hostPort: "61118"                 # kubectl 이 붙는 포트
ports:
  - port: 8081:80                   # Ingress HTTP 진입
    nodeFilters: [loadbalancer]
  - port: 8443:443                  # Ingress HTTPS 진입
    nodeFilters: [loadbalancer]
```

```bash
k3d cluster create --config k3d-lab.yaml
```

### 확인

```bash
kubectl get nodes -o wide
# NAME               STATUS   ROLES                  VERSION
# k3d-lab-server-0   Ready    control-plane,master   v1.35.5+k3s1   ← SQLite 라 etcd 없음
# k3d-lab-agent-0    Ready    <none>                 v1.35.5+k3s1
# k3d-lab-agent-1    Ready    <none>                 v1.35.5+k3s1

kubectl get pods -A                     # coredns, traefik, local-path-provisioner 가 Running 이 될 때까지 대기
docker ps --filter name=k3d-lab --format '{{.Names}}'
docker port k3d-lab-serverlb            # 80→8081, 443→8443, 6443→61118
```

## lab3 — server 3 겸임

### 명령 한 줄

```bash
k3d cluster create lab3 \
  --servers 3 \
  --agents 0 \
  --image rancher/k3s:v1.35.5-k3s1 \
  --api-port 127.0.0.1:61119 \
  -p "8082:80@loadbalancer" \
  -p "8444:443@loadbalancer"
```

### 설정 파일

```yaml
# k3d-lab3.yaml
apiVersion: k3d.io/v1alpha5
kind: Simple
metadata:
  name: lab3
servers: 3                          # 컨트롤 플레인 3개 = 실서버 3대 겸임
agents: 0                           # 워크로드도 server 에서 실행
image: rancher/k3s:v1.35.5-k3s1
kubeAPI:
  hostIP: "127.0.0.1"
  hostPort: "61119"                 # lab 의 61118 과 구분
ports:
  - port: 8082:80
    nodeFilters: [loadbalancer]
  - port: 8444:443
    nodeFilters: [loadbalancer]
```

```bash
k3d cluster create --config k3d-lab3.yaml
```

### 확인

```bash
kubectl get nodes
# NAME                STATUS   ROLES                       VERSION
# k3d-lab3-server-0   Ready    control-plane,etcd,master   v1.35.5+k3s1
# k3d-lab3-server-1   Ready    control-plane,etcd,master   v1.35.5+k3s1
# k3d-lab3-server-2   Ready    control-plane,etcd,master   v1.35.5+k3s1
```

- ROLES 에 `etcd` 가 보이면 내장 etcd 3멤버. server 2개 이상이면 k3d 가 첫 노드에 `--cluster-init` 을 자동으로 넣음
- server 1개짜리 `lab` 은 SQLite 라 `etcd` 가 없음

```bash
docker ps --filter name=k3d-lab3 --format '{{.Names}}'
# k3d-lab3-serverlb      ← API 고정 접점 역할. 6443 을 3대로 분산
# k3d-lab3-server-2
# k3d-lab3-server-1
# k3d-lab3-server-0

kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}'
# https://127.0.0.1:61119   ← 개별 노드가 아니라 serverlb 를 가리킴
```

### 장애 리허설

실서버의 "server 1대 강제 종료" 에 해당하는 것이 `k3d node stop`.

```bash
k3d node stop k3d-lab3-server-1      # 1대 정지
kubectl get nodes                    # 계속 응답. server-1 은 잠시 뒤 NotReady

k3d node stop k3d-lab3-server-2      # 2대째 정지 → etcd 과반(2) 미달
kubectl get nodes                    # 타임아웃. 3대 구성의 한계이며 정상 동작

k3d node start k3d-lab3-server-2     # 1대 복구 → 과반 회복 → API 재개
k3d node start k3d-lab3-server-1
```

- 실서버와 다른 점: serverlb 가 단일 컨테이너라 이것이 죽으면 kubectl 이 끊김. 실서버는 kube-vip 가 VIP 를 옮겨 이 지점도 HA

## 실서버 — RKE2 3대 겸임

k3d `lab3` 를 실서버로 옮긴 형태. 컨테이너 1개 = 머신 1대, serverlb = kube-vip VIP.

**검증 상태.** 위 k3d 절은 실행 결과를 보고 적은 것. 아래 RKE2 절은 RKE2·kube-vip·MetalLB·Longhorn 공식 문서를 기준으로 작성한 절차이며 아직 실서버에서 실행하지 않았음. 실행한 단계는 표의 상태를 날짜로 바꾼다.

| 단계 | 상태 |
| --- | --- |
| 1. 3대 공통 준비 | 미검증 |
| 2. server-1 기동 (kube-vip) | 미검증 |
| 3. server-2, 3 조인 | 미검증 |
| 4. agent 추가 | 미검증 |
| 5. MetalLB + Traefik | 미검증 |
| 6. Longhorn | 미검증 |
| 7. 장애 리허설 | 미검증 |
| 8. 죽은 server 노드 교체 | 미검증 |
| 9. 스냅샷 복원 | 미검증 |
| 10. 업그레이드 | 미검증 |
| 11. 인증서 갱신 | 미검증 |

```text
            k8s-api.example.internal = 10.0.0.10 (kube-vip VIP) ─ 6443 / 9345
                     │
     ┌───────────────┼───────────────┐
  server-1        server-2        server-3
  10.0.0.11       10.0.0.12       10.0.0.13
  etcd            etcd            etcd
  control plane   control plane   control plane
  워크로드        워크로드        워크로드
  Traefik         Traefik         Traefik      ← 진입 VIP 10.0.0.20 (MetalLB)
```

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 역할 | 3대 모두 server, taint 없음 | 3대에서 HA 가 되는 유일한 구성 |
| API 고정 접점 | kube-vip VIP `10.0.0.10` | kubeconfig·조인 주소가 개별 서버를 가리키면 그 서버 장애 시 재연결 불가 |
| CNI | Canal (기본) | 생성 후 변경 불가 |
| Ingress | Traefik (v1.36 기본) | ingress-nginx 는 2026-03 EOL |
| LoadBalancer | MetalLB L2 | RKE2 에는 내장 LB 없음 (k3s ServiceLB 해당 없음) |
| 스토리지 | Longhorn 복제 3 | 노드 장애 시 볼륨 이동 |
| etcd 백업 | 6시간마다 S3(MinIO) | 로컬 스냅샷은 노드와 함께 사라짐 |
| CIS 프로파일 | 처음엔 끔 | `restricted` PSA 가 준비 안 된 워크로드 거부. 파일럿 후 활성화 |

사양: 대당 8 vCPU, 16GB 이상, OS·etcd 용 SSD + Longhorn 용 SSD.

### 1. 3대 공통 준비

```bash
sudo hostnamectl set-hostname server-1          # 2, 3 도 각각. 클러스터 안에서 유일해야 함
timedatectl status | grep "synchronized: yes"   # 시간 동기화

# Longhorn 사전 패키지 (RHEL 계열. Ubuntu 는 open-iscsi nfs-common cryptsetup dmsetup)
sudo dnf install -y iscsi-initiator-utils nfs-utils cryptsetup device-mapper
sudo systemctl enable --now iscsid
sudo modprobe iscsi_tcp && echo iscsi_tcp | sudo tee /etc/modules-load.d/iscsi_tcp.conf

# Longhorn 용 SSD 마운트 (장치명은 lsblk 로 확인. 예: /dev/nvme1n1)
sudo mkfs.ext4 -L longhorn /dev/nvme1n1
sudo mkdir -p /data/longhorn
echo 'LABEL=longhorn /data/longhorn ext4 defaults,nofail 0 2' | sudo tee -a /etc/fstab
sudo mount -a && df -h /data/longhorn          # 6. Longhorn 의 defaultDataPath 가 이 경로

# 방화벽 (firewalld 를 켜 둘 경우)
sudo firewall-cmd --permanent --add-port={6443,9345,2379,2380,10250}/tcp   # 클러스터 내부
sudo firewall-cmd --permanent --add-port=8472/udp                          # Canal VXLAN
sudo firewall-cmd --permanent --add-port={80,443}/tcp                      # Ingress
sudo firewall-cmd --permanent --add-port=3260/tcp                          # Longhorn iSCSI
sudo firewall-cmd --permanent --add-port=7946/{tcp,udp}                    # MetalLB speaker
sudo firewall-cmd --reload

openssl rand -hex 32     # → 토큰. 3대 같은 값. 복구용으로 보관. config.yaml 에는 이 값을 그대로 적음 (아래 참고)
```

| 포트 | 용도 | k3s 와 차이 |
| --- | --- | --- |
| 6443 | Kubernetes API | 같음 |
| **9345** | RKE2 supervisor (노드 등록) | k3s 는 6443 하나로 처리. RKE2 는 조인 주소가 9345 |
| 2379-2380 | etcd | 같음 |
| 10250 | kubelet | 같음 |
| 8472/udp | VXLAN | 같음 |

### 2. server-1 — kube-vip 를 먼저 두고 기동

`/var/lib/rancher/rke2/server/manifests/` 아래 YAML 은 기동 시 자동 배포. kube-vip 를 여기 두면 첫 기동과 함께 VIP 가 올라옴.

```bash
sudo mkdir -p /etc/rancher/rke2 /var/lib/rancher/rke2/server/manifests
curl -sL https://kube-vip.io/manifests/rbac.yaml \
  | sudo tee /var/lib/rancher/rke2/server/manifests/kube-vip-rbac.yaml >/dev/null
```

```yaml
# /var/lib/rancher/rke2/server/manifests/kube-vip.yaml  (vip_interface 는 ip -br link 로 확인)
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: kube-vip-ds
  namespace: kube-system
spec:
  selector:
    matchLabels:
      name: kube-vip-ds
  template:
    metadata:
      labels:
        name: kube-vip-ds
    spec:
      hostNetwork: true
      serviceAccountName: kube-vip
      nodeSelector:
        node-role.kubernetes.io/control-plane: "true"
      tolerations:
        - effect: NoSchedule
          operator: Exists
        - effect: NoExecute
          operator: Exists
      containers:
        - name: kube-vip
          image: ghcr.io/kube-vip/kube-vip:v1.2.4     # 릴리스 페이지에서 최신 태그 확인
          imagePullPolicy: IfNotPresent
          args: ["manager"]
          env:
            - { name: vip_arp, value: "true" }
            - { name: port, value: "6443" }
            - { name: vip_interface, value: eth0 }
            - { name: vip_cidr, value: "32" }
            - { name: cp_enable, value: "true" }
            - { name: cp_namespace, value: kube-system }
            - { name: svc_enable, value: "false" }
            - { name: vip_leaderelection, value: "true" }
            - { name: vip_leaseduration, value: "5" }
            - { name: vip_renewdeadline, value: "3" }
            - { name: vip_retryperiod, value: "1" }
            - { name: address, value: 10.0.0.10 }
          securityContext:
            capabilities:
              add: ["NET_ADMIN", "NET_RAW"]
```

ARP 모드 = VIP 가 한 노드에 붙어 있고, 그 노드가 죽으면 리더 선출로 다른 노드가 가져감. 모든 포트(9345 포함)가 함께 옮겨가므로 조인 주소도 VIP 사용 가능.

**`${RKE2_TOKEN}` 같은 표기는 이 노트의 자리표시자.** `config.yaml` 은 셸이 아니라 YAML 이라 환경변수를 풀어주지 않으므로 실제 값을 직접 적는다. 값을 파일에 남기기 싫으면 템플릿을 두고 `envsubst < config.yaml.tpl | sudo tee /etc/rancher/rke2/config.yaml` 로 생성. 어느 쪽이든 결과 파일은 `chmod 600`.

```yaml
# /etc/rancher/rke2/config.yaml  (server-1)
token: ${RKE2_TOKEN}                       # 자리표시자. 실제 토큰 문자열을 적음
tls-san:
  - k8s-api.example.internal
  - 10.0.0.10                              # VIP. SAN 에 없으면 VIP 접속이 TLS 오류
cni: canal
ingress-controller: traefik
write-kubeconfig-mode: "0640"
etcd-expose-metrics: true                  # Prometheus 수집
etcd-snapshot-schedule-cron: "0 */6 * * *"
etcd-snapshot-retention: 20
etcd-s3: true
etcd-s3-endpoint: minio.example.internal:9000
etcd-s3-bucket: rke2-etcd-snapshots
etcd-s3-folder: prod
etcd-s3-access-key: ${S3_ACCESS_KEY}
etcd-s3-secret-key: ${S3_SECRET_KEY}
# etcd-s3-insecure: true                   # MinIO 가 HTTP 라면
# profile: cis                             # 파일럿 후
```

```bash
curl -sfL https://get.rke2.io | sh -
sudo systemctl enable --now rke2-server.service
sudo journalctl -u rke2-server -f          # "rke2 is up and running" 까지 1~3분

export KUBECONFIG=/etc/rancher/rke2/rke2.yaml
export PATH=$PATH:/var/lib/rancher/rke2/bin
kubectl get nodes                          # server-1 Ready
kubectl -n kube-system get pods | grep kube-vip
ping -c1 10.0.0.10                          # VIP 응답
```

| 경로 | 내용 |
| --- | --- |
| `/etc/rancher/rke2/config.yaml` | 설정. k3s 의 `/etc/rancher/k3s/config.yaml` |
| `/etc/rancher/rke2/rke2.yaml` | 관리자 kubeconfig |
| `/var/lib/rancher/rke2/server/node-token` | 조인 토큰 |
| `/var/lib/rancher/rke2/bin/` | kubectl, crictl. PATH 에 없음 |
| `/var/lib/rancher/rke2/server/manifests/` | 자동 배포 YAML (HelmChart 포함) |

### 3. server-2, server-3 조인

config 는 server-1 과 같고 `server:` 한 줄 추가. kube-vip 매니페스트는 다시 넣지 않음.

```yaml
# /etc/rancher/rke2/config.yaml  (server-2, server-3)
server: https://10.0.0.10:9345             # VIP. server-1 IP 를 적으면 server-1 장애 시 재조인 실패
token: ${RKE2_TOKEN}
tls-san:
  - k8s-api.example.internal
  - 10.0.0.10
cni: canal
ingress-controller: traefik
write-kubeconfig-mode: "0640"
etcd-expose-metrics: true
# etcd-snapshot-*, etcd-s3-* 는 server-1 과 동일
```

```bash
curl -sfL https://get.rke2.io | sh -
sudo systemctl enable --now rke2-server.service
```

**한 대씩.** server-2 가 Ready 된 뒤 server-3. 동시에 조인하면 etcd 멤버 추가 충돌.

```bash
kubectl get nodes -o wide                                   # 3대 Ready, ROLES control-plane,etcd,master
kubectl -n kube-system get pods -l component=etcd            # etcd-server-1/2/3 Running

# 운영 PC kubeconfig 는 VIP 이름으로
scp server-1:/etc/rancher/rke2/rke2.yaml ~/.kube/rke2.yaml
sed -i 's|https://127.0.0.1:6443|https://k8s-api.example.internal:6443|' ~/.kube/rke2.yaml      # Linux
sed -i '' 's|https://127.0.0.1:6443|https://k8s-api.example.internal:6443|' ~/.kube/rke2.yaml   # macOS 는 -i 뒤에 '' 필요
```

### 4. agent 추가 (5대 이상으로 갈 때)

```yaml
# /etc/rancher/rke2/config.yaml  (agent)
server: https://10.0.0.10:9345
token: ${RKE2_TOKEN}
```

```bash
curl -sfL https://get.rke2.io | INSTALL_RKE2_TYPE="agent" sh -
sudo systemctl enable --now rke2-agent.service
```

agent 를 두기 시작하면 server 에 taint 를 걸어 컨트롤 플레인 보호 ([[구성도]] 5대 이상 구성).

### 5. MetalLB + Traefik

RKE2 에는 ServiceLB 가 없어 Traefik 의 LoadBalancer 서비스가 `<pending>` 에 멈춤. server-1 한 곳에만 둠.

**파일을 둘로 나눈다.** `IPAddressPool`·`L2Advertisement` 는 MetalLB 차트가 CRD 를 만든 뒤에야 apply 되는 리소스. HelmChart 와 한 파일에 두면 CRD 가 생기기 전 apply 가 실패하고 `rke2-server` 로그에 `no matches for kind "IPAddressPool"` 가 찍힌다. 매니페스트 디렉터리는 파일 단위로 재시도하므로 몇 분 뒤 저절로 성공하지만, 분리해 두면 로그 오류 없이 한 번에 들어가고 나중에 IP 대역만 바꿀 때도 차트를 건드리지 않는다.

```yaml
# /var/lib/rancher/rke2/server/manifests/metallb.yaml  — 차트
apiVersion: helm.cattle.io/v1
kind: HelmChart
metadata:
  name: metallb
  namespace: kube-system
spec:
  repo: https://metallb.github.io/metallb
  chart: metallb
  targetNamespace: metallb-system
  createNamespace: true
```

```yaml
# /var/lib/rancher/rke2/server/manifests/metallb-config.yaml  — IP 대역. 차트가 뜬 뒤 넣거나, 같이 넣고 재시도에 맡김
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: ingress-pool
  namespace: metallb-system
spec:
  addresses:
    - 10.0.0.20-10.0.0.29               # API VIP·노드 IP·DHCP 와 겹치지 않게
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: ingress-l2
  namespace: metallb-system
```

```bash
kubectl -n metallb-system get pods                          # controller, speaker×3 Running
kubectl get ipaddresspools -n metallb-system                # ingress-pool. 안 보이면 CRD 전 apply 실패 → 재시도 대기 또는 파일을 touch
```

### 8. 죽은 server 노드 교체

3대 중 1대가 복구 불가(디스크·하드웨어 고장)일 때. **2대가 살아 있어 kubectl 이 응답하는 동안**만 이 절차. 2대가 죽었으면 9. 스냅샷 복원으로.

흐름: 죽은 노드를 클러스터에서 지움 → etcd 멤버가 2개로 줄어듦 → 새 머신을 같은 이름으로 조인 → 다시 3개.

#### 8-1. 상태 확인 (살아 있는 server 에서)

```bash
export KUBECONFIG=/etc/rancher/rke2/rke2.yaml PATH=$PATH:/var/lib/rancher/rke2/bin
kubectl get nodes                                    # server-3 NotReady
ping -c1 10.0.0.10                                    # VIP 응답. 죽은 노드가 VIP 를 갖고 있었어도 수 초 안에 이동

# etcd 멤버 목록. etcdctl 은 etcd Pod 안에 있음
kubectl -n kube-system exec etcd-server-1 -- sh -c '
  ETCDCTL_API=3 etcdctl \
    --endpoints=https://127.0.0.1:2379 \
    --cacert=/var/lib/rancher/rke2/server/tls/etcd/server-ca.crt \
    --cert=/var/lib/rancher/rke2/server/tls/etcd/server-client.crt \
    --key=/var/lib/rancher/rke2/server/tls/etcd/server-client.key \
    member list -w table'
# 3개. server-3 도 아직 멤버로 남아 있음 (죽었을 뿐 제거된 게 아님)
```

- 노드가 NotReady 가 된 지 5분이 지나면 Deployment Pod 는 다른 노드로 옮겨감
- StatefulSet Pod 와 볼륨 붙은 Pod 는 `Terminating` 에 멈춤. 노드를 지우면(8-2) 풀림
- Longhorn 볼륨은 복제 3 중 1개를 잃어 `Degraded`. 남은 2대에는 같은 볼륨 복제본이 이미 있어 재구축이 안 됨 → 새 노드가 붙을 때까지 Degraded 유지. 정상

#### 8-2. 죽은 노드 제거

```bash
kubectl delete node server-3
```

RKE2 는 Node 오브젝트가 지워지면 etcd 멤버도 같이 제거한다 (etcd 컨트롤러가 처리). `etcdctl member remove` 를 직접 칠 필요 없음.

```bash
# 위 member list 다시 → 2개
kubectl -n kube-system get secret | grep server-3          # 노드 비밀번호 시크릿 (server-3.node-password.rke2)
```

- 이 시크릿은 노드 삭제 시 함께 지워지는 것이 정상. 남아 있으면 `kubectl -n kube-system delete secret server-3.node-password.rke2`. 남긴 채 같은 이름으로 조인하면 `node password rejected` 로 등록 실패
- Longhorn 노드 항목은 같은 이름으로 재조인하면 그대로 재사용됨. 이름을 바꿀 때만 `kubectl -n longhorn-system delete nodes.longhorn.io server-3`

#### 8-3. 새 머신 준비·조인

1. 3대 공통 준비를 그대로. **호스트명은 죽은 노드와 같은 `server-3`** (Longhorn 노드 항목·라벨·모니터링 대시보드가 이름을 따라감). config 는 3. server-2, server-3 조인과 동일.

```yaml
# /etc/rancher/rke2/config.yaml  (새 server-3)
server: https://10.0.0.10:9345             # VIP. 살아 있는 특정 노드 IP 를 적지 않음
token: <RKE2 토큰>                          # 처음 생성 때 보관한 값
tls-san:
  - k8s-api.example.internal
  - 10.0.0.10
cni: canal
ingress-controller: traefik
write-kubeconfig-mode: "0640"
etcd-expose-metrics: true
# etcd-snapshot-*, etcd-s3-* 는 server-1 과 동일
```

```bash
curl -sfL https://get.rke2.io | sh -
sudo systemctl enable --now rke2-server.service
sudo journalctl -u rke2-server -f                  # "rke2 is up and running"
```

```bash
kubectl get nodes                                  # 3대 Ready
# member list 다시 → 3개, 새 ID 로 등록됨
kubectl -n kube-system get pods -l component=etcd  # etcd-server-3 Running
kubectl -n longhorn-system get volumes.longhorn.io # 잠시 뒤 Degraded → Healthy (복제본 재구축)
```

- 죽은 노드가 **server-1** 이었다면 `/var/lib/rancher/rke2/server/manifests/` 의 kube-vip·metallb·longhorn YAML 원본이 함께 사라진 것. 클러스터 안의 리소스(DaemonSet, HelmChart)는 etcd 에 있어 무사하므로 동작에는 지장 없음. 나중에 수정할 때를 위해 원본 YAML 을 새 노드(또는 git)에 다시 둠. 다시 넣어도 이미 있는 리소스라 덮어쓸 뿐
- 옮겨간 Pod 는 저절로 돌아오지 않음. 분산이 필요하면 `kubectl rollout restart deployment/<name>`

#### 8-4. 죽은 줄 알았던 머신이 다시 켜졌을 때

옛 디스크의 `rke2-server` 가 그대로 뜨면 이미 제거된 멤버 ID 로 etcd 에 붙으려다 실패를 반복한다. 되살려 쓰려면 데이터를 지우고 새 노드처럼 조인.

```bash
sudo systemctl stop rke2-server
sudo rm -rf /var/lib/rancher/rke2/server/db        # etcd 데이터. 이후는 8-3 과 동일
sudo systemctl start rke2-server
```

이미 새 `server-3` 을 붙였다면 이 머신은 절대 켜지 않거나 `rke2-uninstall.sh` 로 정리. 같은 호스트명 두 대가 등록을 다투게 됨.

#### 2대가 죽었을 때 (참고)

과반 미달이라 kubectl 이 안 된다. 남은 1대에서 단일 멤버로 reset 한 뒤 나머지를 새로 조인.

```bash
sudo systemctl stop rke2-server
sudo rke2 server --cluster-reset                   # 스냅샷 없이 현재 데이터로 1멤버 etcd 재구성
sudo systemctl start rke2-server
# 이후 나머지 2대는 8-2 (delete node) → 8-3 (조인)
```

reset 시점의 데이터를 그대로 쓰므로 S3 스냅샷 복원(9)보다 먼저 시도. 남은 1대의 디스크까지 의심스러우면 9 로.

### 9. 스냅샷 복원

```bash
# 모든 server 정지 → server-1 에서 S3 스냅샷으로 reset → 나머지는 db 삭제 후 재조인
sudo rke2 etcd-snapshot list                                      # 스냅샷 이름 확인 (S3 포함)
sudo systemctl stop rke2-server                                   # 3대
sudo rke2 server --cluster-reset \
  --cluster-reset-restore-path=<스냅샷 파일명> \
  --etcd-s3 --etcd-s3-endpoint=minio.example.internal:9000 \
  --etcd-s3-bucket=rke2-etcd-snapshots --etcd-s3-folder=prod \
  --etcd-s3-access-key=<S3 키> --etcd-s3-secret-key=<S3 시크릿>
sudo systemctl start rke2-server                                  # server-1
sudo rm -rf /var/lib/rancher/rke2/server/db && sudo systemctl start rke2-server   # server-2, 3
```

### 10. 업그레이드

원칙: **server 먼저, 한 대씩, 마이너 한 단계씩.** Kubernetes 는 마이너 버전을 건너뛰는 업그레이드를 지원하지 않음 (1.35 → 1.37 불가, 1.36 을 거침).

#### 10-1. 사전 확인

```bash
kubectl get nodes                          # 3대 Ready, 현재 버전
rke2 --version
sudo rke2 etcd-snapshot save --name pre-upgrade     # 수동 스냅샷. S3 설정이 있으면 S3 에도 올라감
sudo rke2 etcd-snapshot list | grep pre-upgrade
kubectl -n longhorn-system get volumes.longhorn.io  # 전부 Healthy. Degraded 가 있으면 먼저 복구
```

- 목표 버전은 Rancher 지원 매트릭스(https://www.suse.com/suse-rancher/support-matrix/) 에서 Rancher 버전과 맞는지 확인. Rancher 가 지원 안 하는 Kubernetes 로 올리면 Rancher UI 에서 클러스터가 Unavailable
- RKE2 릴리스 노트에서 해당 버전의 Canal·Traefik·containerd 변경 확인. Traefik 은 메이저가 바뀌면 IngressRoute CRD 버전이 달라질 수 있음
- 패치만 올릴 때(1.36.4 → 1.36.7)는 드레인 없이 재시작만 해도 되지만, 절차를 하나로 유지하기 위해 항상 같은 순서로

#### 10-2. 한 대씩 (server-1 → 2 → 3, 그 다음 agent)

```bash
# [운영 PC] 1) 새 Pod 배치 막고 기존 Pod 비우기
kubectl cordon server-1
kubectl drain server-1 --ignore-daemonsets --delete-emptydir-data --timeout=300s

# [server-1] 2) 새 버전 설치 후 재시작. 채널로 지정하면 그 마이너의 최신 패치
curl -sfL https://get.rke2.io | sudo INSTALL_RKE2_VERSION=v1.36.4+rke2r1 sh -
# 또는  curl -sfL https://get.rke2.io | sudo INSTALL_RKE2_CHANNEL=v1.36 sh -
sudo systemctl restart rke2-server
sudo journalctl -u rke2-server -f          # "rke2 is up and running"

# [운영 PC] 3) 확인 후 다시 열기
kubectl get nodes                          # server-1 Ready, VERSION 이 새 버전
kubectl -n kube-system get pods -l component=etcd    # 3개 Running
kubectl uncordon server-1
kubectl -n longhorn-system get volumes.longhorn.io  # Healthy 로 돌아온 뒤 다음 대
```

- **drain 이 멈추면** Longhorn 이 막는 것. 어떤 볼륨의 마지막 정상 복제본이 이 노드에 있으면 Longhorn PDB 가 축출을 거부. `kubectl -n longhorn-system get volumes.longhorn.io` 에서 Degraded 볼륨을 찾아 복구를 기다린 뒤 재시도. 3대에 복제 3 이고 전부 Healthy 면 걸리지 않음
- **VIP 보유 노드를 재시작하면** kube-vip 리더가 바뀌어 kubectl 이 수 초 끊김. 정상
- agent 가 있으면 server 3대가 끝난 뒤 같은 순서로. agent 는 `rke2-agent.service`
- 컨트롤 플레인이 워커보다 항상 같거나 높은 버전이어야 함. 그래서 server 먼저

#### 10-3. 자동화 (system-upgrade-controller)

노드가 늘어나면 SUC 를 설치하고 `Plan` 리소스에 버전을 적으면 컨트롤러가 위 순서(cordon → drain → 설치 → uncordon)를 노드마다 반복. 3대 겸임에서는 수동이 더 안전. 도입 시점은 agent 가 3대를 넘을 때.

### 11. 인증서 갱신

RKE2 가 만드는 인증서는 **CA 10년, 나머지(API 서버·kubelet·etcd·kubeconfig 클라이언트) 1년.** 만료되면 kubectl 이 `x509: certificate has expired` 로 끊기고 컴포넌트끼리도 통신이 안 된다.

**자동 갱신 조건: 만료 90일 이내이거나 이미 만료된 상태에서 `rke2-server` 가 재시작될 때.** 재시작이 없으면 갱신도 없음. 1년 넘게 재시작 없이 돌면 만료로 정지한다.

```bash
# 만료일 확인
sudo rke2 certificate check                                # 인증서별 만료일과 남은 일수 (v1.28 이후)
sudo openssl x509 -noout -enddate \
  -in /var/lib/rancher/rke2/server/tls/serving-kube-apiserver.crt   # 구버전이면 이걸로
sudo openssl x509 -noout -enddate \
  -in /var/lib/rancher/rke2/server/tls/client-admin.crt             # rke2.yaml 이 쓰는 인증서
```

#### 만료 90일 이내 (정상 경로)

```bash
sudo systemctl restart rke2-server         # 한 대씩. 재시작 로그에 "certificate ... rotated"
sudo rke2 certificate check                # 1년 뒤로 밀렸는지
```

10. 업그레이드를 1년에 한 번 이상 하면 그 재시작으로 자동 갱신되므로 따로 할 일이 없음. 업그레이드를 미루더라도 **11개월째에 재시작 한 번**은 달력에 둔다.

#### 90일보다 많이 남았는데 미리 갱신하고 싶을 때

```bash
sudo systemctl stop rke2-server
sudo rke2 certificate rotate               # 서비스 정지 상태에서만 가능
sudo systemctl start rke2-server
```

#### 이미 만료된 뒤

재시작하면 만료된 것도 갱신된다. 다만 kubectl 이 안 되므로 각 노드에 SSH 로 들어가 한 대씩 재시작.

```bash
sudo systemctl restart rke2-server         # 3대 순서대로
export KUBECONFIG=/etc/rancher/rke2/rke2.yaml
kubectl get nodes                          # 노드 안에서는 새 rke2.yaml 로 바로 됨
```

- 어느 경로든 `client-admin` 인증서가 바뀌므로 **운영 PC 의 kubeconfig 는 다시 복사** (3. 조인 끝의 scp·sed). 옛 kubeconfig 는 `x509: certificate signed by unknown authority` 가 아니라 `expired` 로 실패하니 구분 가능
- 노드 비밀번호·토큰은 인증서와 무관. 재조인 필요 없음
- Longhorn·MetalLB·Traefik 은 ServiceAccount 토큰을 쓰므로 영향 없음. cert-manager 가 발급하는 앱 TLS 인증서는 별개 (Rancher 노트에서 다룸)

### k3s ↔ RKE2 명령 대응

| | k3s | RKE2 |
| --- | --- | --- |
| 설치 | `curl -sfL https://get.k3s.io \| sh -` | `curl -sfL https://get.rke2.io \| sh -` |
| agent 설치 | `K3S_URL=... K3S_TOKEN=... sh -` | `INSTALL_RKE2_TYPE="agent" sh -` + config 의 `server:`/`token:` |
| 서비스 | `k3s.service` | `rke2-server.service`, `rke2-agent.service` |
| 설정 | `/etc/rancher/k3s/config.yaml` | `/etc/rancher/rke2/config.yaml` |
| kubeconfig | `/etc/rancher/k3s/k3s.yaml` | `/etc/rancher/rke2/rke2.yaml` |
| 토큰 | `/var/lib/rancher/k3s/server/node-token` | `/var/lib/rancher/rke2/server/node-token` |
| kubectl | `k3s kubectl` 내장 | `/var/lib/rancher/rke2/bin/kubectl` |
| 조인 포트 | 6443 | 9345 |
| 내장 LB | ServiceLB 있음 | 없음 → MetalLB |
| 기본 StorageClass | local-path 있음 | 없음 → Longhorn |
| HA 첫 노드 | `--cluster-init` | 자동 (etcd 고정) |
